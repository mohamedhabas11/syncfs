| etcd snapshots are periodic Raft snapshots + CRC; compaction keeps `snapshot-count` entries | §8.5 snapshot description | https://etcd.io/docs/v3.6/learning/persistent-storage-files/ | "This document explains the etcd persistent storage format: naming, content and tools… bbolt b+tree: the main etcd content …" (page title: "etcd persistent storage files") | **Comparison point** — etcd snapshot = bbolt checkpoint + WAL. **Verdict on GC safety rule:** The spec's rule is a *necessary* invariant (no naive refcount GC) but insufficient alone. It needs: epoch protocol (Raft index/term when mark was taken; sweep only after commit advances past grace), snapshot pinning (Pebble snapshot or Raft snapshot must be a root for the whole mark→sweep window), and lease in-flight pinning across leader epochs. Without these, a chunk referenced by an *uncommitted in-flight operation that later commits* can be swept early. This is the classic distributed-GC hazard (see backtracing paper).

## 6. Content-addressed index consistency — concurrent same-hash writes

Spec has **no rule** for two nodes writing the same `ChunkID` concurrently (e.g. leader + follower race, or two different offsets containing identical bytes).

- Root cause: chunk index key = `ChunkID` (32 bytes). Two writers inserting the same hash with different pack offsets or generations = duplicate rows / last-writer-wins.
- Why "dedup race is safe because bytes are identical" is *mostly* true for data but *unsafe* for metadata: pack offset, generation, refcount, and manifest extent mapping can diverge. If follower B's pack offset wins but leader A's Pebble entry is the one other replicas see, reads after leader failover fetch from a non-existent offset → hash-valid data at the wrong location = availability loss (not corruption, but violates §4 #4).
- Fix: single-writer discipline — only the leader prepares chunks (§8.2 steps 4–5 already imply this, but §6 dedup is unstated). Index insert must be idempotent: `INSERT OR IGNORE` keyed by `(ChunkID, generation)` with offset stored once; followers adopt leader's offset from the *committed manifest* rather than their own staging offset. Concurrent same-hash from *different* leaders is impossible under Raft single-leader §5.2, but **same-hash from leader + async learner staging** must be defined.

A 1 TiB volume with dense files = ~16 M extents ≈ 16 M × (32-byte hash + 8-byte offset + 12-byte len/off) ≈ **~800 MiB uncompressed** | §8.5; §7.3 `FileManifest{Size, Extents []Extent}` | (arithmetic from spec's own struct definitions) | Medium volumes are fine; large volumes produce **hundreds of MiB snapshots** that must cross a 10 GbE LAN to a learner (§11 ref hardware). No compression (Snappy/Zstd), no streaming, no differential snapshot, and no *manifest size bound* stated. etcd solves this with `snapshot-count` compaction; SyncFS needs an equivalent or a manifest record cap tied to §7.2 `MaxFileBytes`. |

**Verdict on snapshots:** Design direction (checkpoint + manifest, receiver verifies hashes, replays log) matches etcd/TiKV/CockroachDB practice. **Format, versioning, and size are underspecified** — see §4.

## 9. Concrete corrections proposed (addendum to spec — not editing spec files per instructions)

1. **§6 Pebble cell** → expand to: "Embedded LSM ordered KV (WAL + memtable + L0–L6 SSTables, level-based compaction). Production at scale in CockroachDB since v20.2. BSD-3-Clause. Write batches MUST use `WriteOptions.Sync` when gating a durable receipt. `FormatMajorVersion` is pinned per volume; nodes refuse to open a DB whose format major version is not in the volume's allowed set (§4 #9). Write-amp budget: `Metrics.WriteAmp()` reported in §11 benchmark." *(URLs: github.com/cockroachdb/pebble, pkg.go.dev/github.com/cockroachdb/pebble)*
2. **§6 BLAKE3 cell** → add: "BLAKE3-256 (128-bit collision resistance). Faster than SHA-2/SHA-3 per reference implementation; measure 4 KiB single-thread on target CPU before claiming §11 headroom. Not NIST/RFC-standard: informational I-D draft-aumasson-blake3-00 + C2SP; adopt only with FIPS waiver if needed." *(URLs: github.com/BLAKE3-team/BLAKE3, ietf draft-aumasson-blake3-00)*
3. **§7.5 local layout** → add pack record format + recovery rule: header/footer CRC, length bounds, dir-fsync after create/rename, scan-and-truncate-tail on open, verify pack offsets against Pebble index before serving reads. *(Consequence of man-pages fsync(2) dir-entry rule + ext4 data=ordered.)*
4. **§8.2 step 4** → change "force it durable" to: "append to pack, `fdatasync()` pack fd, `fsync()` pack parent directory on create/rename, `fdatasync()` staging rename + `fsync()` staging parent; issue receipt only after Pebble `SyncWait()` returns." *(Same sources.)*
5. **§8.5 snapshot** → define envelope + version + compression (zstd) + streaming transfer + manifest hash; state that receiver verifies metadata CRC **and** every chunk in `chunkManifest` before activation; state manifest size cap = `MaxFileBytes / ChunkSizeBytes`. *(Comparison: etcd persistent-storage-files + pebble Checkpoint API.)*
6. **§8.5 GC** → replace "persisted generation" with epoch protocol: `markIndex`, grace = +snapshots, two-cycle sweep, in-flight pinning. *(Sources: mark-and-sweep + distributed backtracing literature.)*
7. **§7.3 truncate** → add canonical hole/truncate rules (G5). **§7.2/§8.2 quota** → add projected-usage admission check (G6–G7).
8. **§11** → add Pebble WriteAmp query, PLP status recording, dir-fsync accounting in benchmark report; re-state "honors flushes" as `data=ordered` + barriers=1 + PLP recorded. *(Source: kernel ext4 docs + fsync man page.)*

## 10. Honesty note

- **This audit read only the three targets above.** No implementation exists; all §8/M-tasks are future work. Verdicts are therefore spec-vs-primary-source, not code-vs-test.
- **Web evidence is quoted verbatim** in the table; where `webfetch` returned navigation chrome (e.g. etcd docs, GitHub README) the excerpt is the first substantive paragraph. Full page text was not needed to validate the claim.
- **Chunk-size evidence is weakest:** no primary source gives a single "correct" 64 KiB answer; GFS 64 KB blocks, XFS 64 KB FS blocks, and ZFS variableization show 64 KiB is *common*, not *proven optimal*. §11 benchmarks must settle it.
- **Pebble `WriteOptions` semantics:** the pkg.go.dev excerpt is explicit that `Sync:true` triggers WAL fsync; the converse (default no-sync) is inferred from the API shape and PostgreSQL/RocksDB practice. M2-02 must confirm against the pinned Pebble version's docs before implementation.
- **ext4/XFS PLP:** kernel docs + man pages describe ordered/barrier semantics; real PLP behavior is device-specific and cannot be verified without hardware. Spec's §11 "records storage flush behavior" only helps if M5-01 runs power-loss (not just process-kill) tests — see §13 fault matrix.
- **BLAKE3 small-input caveat:** the "slower than SHA-256 for small inputs" data point comes from a forum benchmark, not a primary paper. It is flagged as a *measure-don't-assume* risk for the §11 4 KiB gate, not as a disqualifier.
- No spec file was edited. This document is the complete deliverable for Domain Agent 4.
- **Fork-closure compliance:** this revision was re-aligned to the unified baseline (07 §3.5/D-001) without re-litigating the data path. Camp B's taxonomy/quarantine/POSIX-apply/witness contributions are adopted in §9; `hashicorp/raft` and watcher/pull-based MVP paths are treated as superseded throughout (no hashicorp FSM gluing is proposed for chunk gating).
