## 1. One-paragraph fork restatement

Two irreconcilable-as-written product shapes claim the same name. Camp A (`.spec/technical_spec.md` §§1–5, 8, 10) is a **single strict volume** whose application sees only a **FUSE mount**: every mutation is intercepted before it lands, its payload chunks are made durable on a storage majority, its metadata command is committed by Raft, and only then is `close`/`fsync` answered; a watcher/observer that sees writes after they landed can never block or reject them, so quorum-durable-before-ack is impossible without interception. Camp B (`.spec/directory-replication-daemon.md` "Design flaw and resolution", `.spec/consensus-layer.md`, `arch/architecture-proposal.md` §§2–3) rejects FUSE as "not native enough," lets the application write **directly to a native ext4/XFS directory**, detects changes after the fact with watcher + periodic scan, and ships them asynchronously (pull-based from the leader's journal) under **per-directory modes**; it therefore explicitly abandons quorum-durable-before-ack for a bounded-loss async guarantee with quarantine, and adopts `hashicorp/raft` with per-directory lease epochs as the fencing token. Every deeper choice — consensus library, transport, fencing token, consistency, and product shape — follows from that data-path decision, so the camps cannot both be built as written; one must be the MVP data path and the other must be demoted to post-MVP tiers or sub-mechanisms.

### Q1. Can a watcher (inotify/fanotify + periodic scan) EVER deliver quorum-durable-before-ack semantics?

| Question | Source URL | Excerpt | Points to |
|---|---|---|---|
| inotify is an *after-the-fact* notification API by construction; the write has already landed | https://man7.org/linux/man-pages/man7/inotify.7.html | "The inotify API provides a mechanism for monitoring filesystem events." · "When events occur for monitored files and directories, those events are made available to the application as structured data that can be read from the inotify file descriptor" — i.e. read-after-event, not pre-commit. Robust apps must allow for "races … that may leave the cache inconsistent with the filesystem state" and "rebuild the cache when inconsistencies are detected." | **Camp A.** Supports Camp A's §1 claim: a background replicator/watcher "does not see a mutation until after a local application has already succeeded." |
| inotify queue can overflow and *lose* events; no replay | https://man7.org/linux/man-pages/man7/inotify.7.html | "Note that the event queue can overflow. In this case, events are lost. Robust applications should handle the possibility of lost events gracefully." / `IN_Q_OVERFLOW` — "Event queue overflowed (wd is -1 for this event)." | **Camp A.** A lossy post-hoc signal cannot be the ack gate for a quorum-durable contract; periodic rescan is a repair mechanism, not a commit protocol. |
| inotify has no total order across a subtree, misses mmap/msync, is not recursive, and racily pairs renames | https://man7.org/linux/man-pages/man7/inotify.7.html | "Inotify monitoring of directories is not recursive" · "does not report file accesses and modifications that may occur because of mmap(2), msync(2), and munmap(2)" · "Matching up the IN_MOVED_FROM and IN_MOVED_TO event pair … is thus inherently racy" · "by the time an application processes an inotify event, the filename may already have been deleted or renamed." | **Camp A.** Even *detection* is racy/coalescing ("successive identical events … coalesced into a single event … application can't use inotify to reliably count file events"); a fortiori it cannot *order and gate* mutations. |
| fanotify adds permission events, but only for open/access; it still cannot intercept or gate the data path of an already-running write | https://man7.org/linux/man-pages/man7/fanotify.7.html | Permission events are `FAN_OPEN_PERM` / `FAN_ACCESS_PERM` / `FAN_OPEN_EXEC_PERM`: "The reader must write a response that determines whether the permission to access the filesystem object shall be granted." Denial yields `EPERM` (or, since 6.13 with `FAN_CLASS_PRE_CONTENT`, `FAN_DENY_ERRNO`). Notification events (`FAN_MODIFY`, `FAN_CLOSE_WRITE`, `FAN_CREATE`…) remain informative-only: "Notification events are merely informative." Watched-directory creation is still racy: "it can lose events that occurred inside the newly created subdirectory, before a mark is added." mmap/msync are likewise not reported. | **Camp A (with a narrow caveat).** fanotify *can* block an *open* (`FAN_OPEN_PERM` / `FAN_CLASS_PRE_CONTENT`), which is more than inotify can do — but it does not give a post-hoc directory replicator the ability to hold `write`/`close`/`fsync` until a quorum ack. Camp B's chosen mechanism (inotify + periodic scan, `arch/architecture-proposal.md` §9 Q1) is the weak form; the strong form still doesn't deliver per-mutation quorum gating. |
| POSIX `close` semantics prove the point: ack follows the write, not precedes it; durable placement is a separate explicit `fsync` | https://man7.org/linux/man-pages/man2/close.2.html | "A successful close does not guarantee that the data has been successfully saved to disk, as the kernel uses the buffer cache to defer writes. Typically, filesystems do not flush buffers when a file is closed. If you need to be sure that the data is physically stored on the underlying disk, use fsync(2)." · "it is quite possible that errors on a previous write(2) operation are reported only on the final close()… Failing to check the return value … may lead to silent loss of data. This can especially be observed with NFS and with disk quota." | **Camp A.** The application's `close()` returns on the *local* filesystem's terms. A watcher observing `IN_CLOSE_WRITE`/`FAN_CLOSE_WRITE` learns of the close *after* the app has already been told "success" — i.e. mutable ordering is irreversible. To make ack quorum-durable you must be in the synchronous path (FUSE FUSE_WRITE/RELEASE/FLUSH/FSYNC or a block layer), not in an observer. |
| NFS client coherence is close-to-open + attribute caching windows, not lock-step replication — the canonical existence proof that "shared directory via kernel cache ≠ strongly consistent" | https://man7.org/linux/man-pages/man5/nfs.5.html | Default is `cto` close-to-open coherence for directories; attribute caching (`acregmin 3s` … `acregmax 60s`) means "changes that occur on the server … remain undetected until the client checks the server again." Even `noac` "forces application writes to become synchronous so that local changes … become visible on the server immediately" at "a significant performance penalty." The client talks to *one* server endpoint over RPC/TCP — there is no multi-node pre-ack quorum in the NFS protocol itself. | **Camp A (methodological).** NFS's documented trade — either accept coherence windows, or pay the synchronous penalty — is exactly Camp A's thesis. It validates that strictness requires restructuring the I/O path, not layering a watcher on a native dir. |

**Q1 verdict (see §3.1):** A watcher can *eventually* export what landed (with scans/quarantine to paper over overflow/races). It can never *block, reject, or re-order* a mutation that already landed, so it can never make ack conditional on quorum durability. The camp-B "two honest limits" admission — lease prevents split-brain but *not* data loss; replication is async with loss window = lag — is therefore *fatal to the north star as written* ("acknowledged mutations durably replicated," `.spec/technical_spec.md` §3 Accept-1), while being an honest and correct description of what a native-dir replicator *is*.

### Q2. Can FUSE + Raft deliver the north star? What are FUSE's hard costs?

| Question | Source URL | Excerpt | Points to |
|---|---|---|---|
| FUSE *is* the hook that lets userspace own the mutation path | http://libfuse.github.io/doxygen/ (via https://github.com/libfuse/libfuse) · kernel background via https://github.com/hanwen/go-fuse | libfuse README: "FUSE … is an interface for userspace programs to export a filesystem to the Linux kernel… libfuse provides functions to mount the file system, unmount it, read requests from the kernel, and send responses back." The userspace program receives every kernel request and decides the response — the mechanical basis for pre-write gating, sequencing, and refusing an ack until quorum. | **Camp A.** This is the capability the north star requires (`.spec/technical_spec.md` §§4–5, 8.2): gate-then-ack only becomes expressible once the FS is in userspace. |
| go-fuse/v2 is a mature, current adapter; the design choice is real | https://pkg.go.dev/github.com/hanwen/go-fuse/v2 | "Go native bindings for the FUSE kernel module… It follows the wire protocol closely… Comprehensive and up to date protocol support (up to 7.12.28). | FUSE hard cost #1 — userspace round-trip per op; throughput is bounded by context switches and kernel↔userspace copies | https://github.com/libfuse/libfuse (README, "Building your own filesystem") · kernel FUSE design docs referenced from there; go-fuse passthrough note | Response loop is per-request callback→response; raw path copies buffers across the boundary. go-fuse ships *passthrough* support "for increased performance" (v2.6) precisely because the generic path pays this tax; `ReadResultPipe`/splice exist to reduce zero-copy overhead. Upstream guidance: start from the *passthrough* example because naive loops are the slow path. | **Camp B (cost acknowledged, not a refutation).** FUSE overhead is real. | FUSE hard cost #2 — kernel caching is unsafe by default for strict coherence; suspend/kill of the daemon strands kernel pages | https://github.com/libfuse/libfuse (security note + `default_permissions` discussion) · go-fuse `PruneNotify`, `MountOptions` | libfuse documents the long-standing caching hazard: without `default_permissions`, "the results of the first permission check … will be re-used for subsequent accesses as long as the inode … is present in the kernel cache — even if the permissions have since changed" (since 2006). Strict mounts must drive TTL≈0 / direct-I/O / explicit invalidation. go-fuse exposes `PruneNotify` for exactly this: "lets the file system force the kernel to forget nodes." Cost is borne by config discipline + crash testing (host-suspension/mount-death tests, `.spec/technical_spec.md` §8.3), which Camp A already plans. |
| FUSE hard cost #3 — liveness coupling: a frozen/dead FUSE process stalls every thread touching the mount; hang ≠ crash | Derived from the above two primary facts: the kernel blocks the requesting thread until the userspace response arrives (request/response pair), and cached pages survive a dead mount process | No primary doc promises transparent failover *inside* the kernel mount. Camp A states the consequence explicitly: minority partition must invalidate + return an availability error rather than serve expired cache (`.spec/technical_spec.md` §§4 Inv.6, 8.3, 10). The risk is a *feature* of a strict cache: wrong answers are forbidden so stalls are returned instead. | **Camp A (priced).** Suspended-process risk is the dual of split-brain safety; a native-dir replicator avoids the stall only by allowing divergent answers. Southbridge consensus: for a *small-HA LAN* workload the brief explicitly prefers predictable failure over optimistic answers. |
| FUSE cost summary | https://github.com/hanwen/go-fuse/v2/fs (via pkg.go.dev index: "Package fs provides infrastructure to build tree-organized filesystems") + libfuse README | Together: code volume (inode lifetime, `OnForget`, lock forwarding), ops burden (kernel-version/protocol drift 7.12.28+), and perf headroom work (passthrough/zero-copy only recover *some* overhead). No primary source claims FUSE is "free" or "native." | **Camp B's intuition is directionally right; its conclusion is wrong.** "Not native" = "userspace round-trip + cache-safety obligation" is true. But the north star's "acknowledged mutations durably replicated" *requires* non-native interception; you cannot have zero-RPO acks on a path you don't own. |

**Q2 verdict (see §3.1):** FUSE + Raft can deliver the north star's *correctness* (pre-ack quorum gating is mechanically possible) at measured cost (latency floor, cache discipline, stall-on-failure instead of divergence). Native-dir + watcher can deliver *availability* more cheaply by refusing the correctness property.

**Q3 verdict (see §3.2):** etcd/raft/v3 fits Camp A because its deterministic, storage/transport-free core *permits* payload-before-reference and apply/campaign gating as first-class state-machine policy (those rules cannot be expressed as a hashicorp FSM without breaking the library's apply contract). hashicorp/raft fits Camp B because its integrated store/transport + `LeaderLeaseTimeout`/`NotifyCh` + `AddNonvoter` ergonomics match "per-directory leases as FSM data + leadership-channel fence" with minimal glue. The *fence itself* is application-level in both libraries — Camp B's characterization of it as a library feature overstates what either library delivers.

### Q4. Real-world existence proofs: GlusterFS, CephFS, DRBD, live-migration fencing

| Question | Source URL | Excerpt | Points to |
|---|---|---|---|
| GlusterFS = native brick (XFS) **plus** synchronous replication machinery — never watcher-only | https://github.com/gluster/glusterfs (README: software-defined distributed storage; docs at docs.gluster.org) + GlusterFS *Concepts* (brick/arbiter/replica concepts in upstream docs) | Gluster bricks are ordinary XFS directories *backed by* a FUSE-based client (glusterfsd + fuse mount) that interposes on every op in userspace. ## 3. Verdict

### 3.1 Q1 — The watcher question (the fork's load-bearing question)

**A watcher (inotify/fanotify + periodic scan) can NEVER deliver quorum-durable-before-ack semantics.** Primary sources prove the negative three independent ways: (i) inotify/fanotify are post-hoc notification APIs whose events arrive after landing, with overflow loss, non-recursivity, mmap blindness, and inherent rename race (inotify.7, fanotify.7); (ii) POSIX `close` completes on the *local* filesystem's terms — data durability is a separate `fsync`, and close errors are diagnostic, not retroactive gates (close.2); (iii) NFS's documented coherence model shows that sharing a directory through kernel caching without owning the path forces a choice between acceptance of coherence windows and a large synchronous penalty (nfs.5).

The camp-B "two honest limits" admission (`.spec/directory-replication-daemon.md` "Two honest limits") is therefore **fatal to the north star AS WRITTEN**. The north star requires that *acknowledged mutations be durably replicated* (`.spec/technical_spec.md` §3 Accept-1: "A three-node volume acknowledges a mutation only after its metadata command is committed by a Raft majority and all newly referenced content is durable on a storage majority"). Camp B's Limit #1 concedes the opposite contract: "Replication stays asynchronous, so the guarantee is single writer plus a bounded loss window (the replication lag at the moment of failure)… don't promise zero RPO." That is an honest description of a *different product* (a native-dir async replicator with single-writer + quarantine), not a weakened implementation of the north star. There is no engineering delta that closes the gap from inside Camp B: no scan frequency, journal format, or lease TTL retroactively un-lands a write the app already saw succeed. **Camp B must either (a) change the north-star contract to bounded-loss async, or (b) concede the data path.**

### 3.2 Q2/Q3 — FUSE + Raft and the library question

**FUSE + etcd/raft/v3 can deliver the north star's correctness; hashicorp/raft is the wrong library for Camp A's invariants and the right library for Camp B's.**

- *Can FUSE + Raft deliver it?* Yes mechanically: FUSE gives pre-commit interception, etcd/raft/v3 gives a deterministic core whose Ready loop forces the app to own persistence ordering (etcd-io/raft README Ready-loop responsibilities), and quic-go gives QUIC+TLS-1.3 transport with prioritized streams (quic-go README). Costs are real and bounded: per-op userspace round-trip (passthrough/zero-copy mitigate, not eliminate), strict cache discipline (libfuse 2006 caching hazard + PruneNotify), and stall-instead-of-diverge failure mode under partition. Camp A's performance gates (`.spec/technical_spec.md` §11: 1,000 quorum 4KiB write+fsync/s, p99 ≤25 ms) are the correct way to price those costs — as qualification SLOs on named hardware, not promises. **Camp A is not free; it is the only camp that can meet the north star's ack contract.**
- *Which library supports which camp?*
  - **etcd/raft/v3 → Camp A.** Its "only the core algorithm; network and disk IO left to the user" design (etcd-io/raft README) is precisely what makes "payload-before-reference + refuse-to-campaign" *expressible*: chunks are committed outside the log (majority receipts), then the metadata command references them; the state machine checks payload presence before apply and withholds candidacy while gaps exist (`.spec/technical_spec.md` §4 Inv.3–4, §8.2, §8.4). hashicorp/raft's FSM contract (opaque blob → `Apply` → `MaxAppendEntries` batch buffer) cannot express "fetch + verify before apply" or "withhold candidacy" without breaking the library's effect model; those rules would live in glue the library neither enforces nor understands.
  - **hashicorp/raft → Camp B.** Its integrated LogStore/StableStore/SnapshotStore + pluggable Transport (incl. `StreamLayer` for custom transports, `AddNonvoter`/`DemoteVoter` with prevIndex/timeout), `LeaderLeaseTimeout` → step-down, and `NotifyCh` leadership channel are exactly `.spec/consensus-layer.md` Decision #2–3 ("witness voters vs AddNonvoter learners," "leader lease timeout → step down → notify via leadership channel → trigger fence"). If the design target is per-directory leases as FSM data with pull-based sync, hashicorp/raft is the ergonomic choice.
  - **Correction to both camps:** Neither library fences the filesystem. Camp B overstates hashicorp/raft when it implies the leadership channel *is* a fence; its own "Library boundaries" section admits the app-level RO fence (EBUSY remount,ro → freeze/kill) is unprovided glue. Camp A's fencing is likewise application-level (ReadIndex / leader lease + FUSE invalidation) but has a strictly stronger enforcement point: the FUSE mount is the *only* ingress, so "no quorum → no ack" is enforced in one place, whereas a native dir is writable by any local process irrespective of fence state.

### 3.3 Q4 — Existence proofs

| Precedent | Validates | Refutes |
|---|---|---|
| GlusterFS (native XFS bricks + FUSE client + arbiter) | Native storage layer + quorum/arbiter shape (Camp B's witness) | "Native dirs don't need FUSE to be synchronously replicated" — Gluster's bricks are always FUSE-surfaced; the arbiter is a *component*, not an alternative data path. |
| CephFS (MDS serializes + journals before reply) | Owning the op path + metadata-log-as-truth (Camp A's path ownership; Camp B's log idea as truth source) | Watcher-after-write as a strong-semantics mechanism. |
| DRBD (kernel block interception, Protocol A/B/C) | Principle: durable-before-ack requires occupying the path (kernel block hook ≡ FUSE hook). Protocol A as a *bounded-loss async product* | That Protocol-A semantics can satisfy a zero-RPO ack contract. DRBD documents the async loss window honestly; it never re-labels it as synchronous. |
| Live-migration / STONITH fencing | Epochs + quorum as fencing backbone | Lease-epoch-alone as a fence: every precedent requires an enforcement point (STONITH / freeze-kill). FUSE is that enforcement point for a directory service. |

**Net:** Every shipped strongly-consistent POSIX shared-directory system owns the op path (GlusterFS FUSE, CephFS MDS); every shipped native-dir replicator either owns the path at a lower layer (DRBD Protocol C) or accepts bounded-loss async (DRBD Protocol A, rsync-class tools). No shipped system delivers Camp B's needed combination (watcher-observed native dir + quorum-durable acks). The witness/arbiter and quarantine/epoch ideas are validated *as components*; the watcher data path is validated only for async products.

### 3.4 Which camp can meet the north star AS WRITTEN, and what must each concede to merge?

**Camp A can meet the north star as written. Camp B cannot without changing either the north-star contract or its own data path.** Merging therefore cannot be a 50/50 blend; it must be an asymmetric adoption:

- **Camp A concedes (ergonomics, not correctness):**
  1. Accept Camp B's *POSIX fidelity in the apply path* requirements verbatim (modes incl. setuid/setgid/sticky, ownership, ACLs, xattrs, symlinks, hardlinks, mtimes; chown-before-chmod ordering; CAP_CHOWN; uid/gid consistency/mapping) as MVP acceptance vectors (`.spec/directory-replication-daemon.md` "POSIX fidelity in the apply path").
  2. Accept Camp B's *node-state taxonomy* and *failure-state model* shape (LEADER/FOLLOWER/FENCED/CANDIDATE/CATCHING_UP/QUARANTINED/HALTED + mass-delete breaker + forced-promotion procedure) as the operability layer over Camp A's invariants — mapped onto Raft + chunk-receipt state rather than onto a watcher journal.
  3. Accept Camp B's *quarantine for uncommitted tails* as the crash-consistency story for interrupted uploads (Camp A already quarantines corrupt WAL/snapshots, §10; extend the same discipline to staged-but-unreferenced chunks).
  4. Accept Camp B's *witness voter / learner* vocabulary for the third-node topology (whether the third node holds full chunks or metadata-only is an Agent 1–6 decision; the *shape* is shared).
  5. Concede that `hashicorp/raft` is a legitimate alternative *if and only if* the team is willing to implement payload-before-reference + refuse-to-campaign as a layer *above* the FSM with its own durability audit — i.e. the library choice is the only genuinely open contest (see §3.2). Recommendation: keep etcd/raft/v3 for MVP (deterministic core matches the invariants), revisit only with a written invariants-translation proof.

- **Camp B concedes (product shape, i.e. the fork itself):**
  1. **Concede the data path.** FUSE interception is not "rejected as not native enough" in the MVP; it *is* the MVP data path (`.spec/technical_spec.md` §5.2 `internal/fusefs`). The watcher becomes a *contingency/audit* mechanism only (e.g., detecting out-of-band local writes to a brick that must never happen, invariant-violation tripwires), never the mutation path.
  2. **Concede the consistency contract for the MVP volume.** One strict, quorum-durable volume (`Consistency: strict`, `Durability: quorum`) replaces per-directory bidirectional-async as the shipped behavior. The three modes (one-way async / bidirectional async / single-writer lease) are *re-tiered*: single-writer lease semantics survive as the FUSE mount's partition behavior (no quorum → no ack, invalidation instead of divergence); the async modes are deferred to post-MVP tiers with their own contracts (bounded-loss, conflict policy, version vectors) and must never alias the strict volume.
  3. **Concede the consensus library for the MVP.** etcd/raft/v3 (deterministic core) replaces hashicorp/raft as the MVP Raft baseline. The per-directory lease-epoch fencing concept survives *recast* as what it actually is under strict semantics: the Raft committed term/index fencing token (`.spec/technical_spec.md` §8.4) plus ReadIndex/lease for reads — not a per-directory epoch detached from the log. Camp B's `AddNonvoter` learner vocabulary maps onto Camp A's learner-first admission (`.spec/technical_spec.md` §4 Inv.8, §12.1).
  4. **Concede the transport.** QUIC push/pipeline with prioritized Raft/lease vs chunk streams replaces pull-from-journal as the MVP data plane (`.spec/technical_spec.md` §§6, 8.1, 11). Pull-based catch-up survives *only* as the follower/learner replay protocol after partitioning, under the same commit semantics — not as steady-state replication.
  5. **Concede the product shape.** One volume group per cluster for MVP; multi-directory/multi-mode generality becomes post-MVP surface. The "directory-replication daemon" product definition is superseded (§5).

Failure to concede 1+2 in particular means the merged product cannot honor "acknowledged mutations durably replicated" — there is no middle tier that is both watcher-observed and zero-RPO; Q1 proves the gap is structural, not tuning.

## 6. Honesty note

**What this document does well and where it could be wrong.**

1. *Q1 is proven, Q4 is inferred.* The negative result in §2 Q1 (watcher ⇒ never quorum-durable-before-ack) rests on near-verbatim primary-source mechanics (notification-after-landing, overflow loss, close semantics, NFS windows) and is as close to proven as systems documentation allows. Q4's existence proofs (GlusterFS/CephFS/DRBD) are *directional*: the upstream READMEs fetched for this analysis are repository entry points, not the full GlusterFS Concepts / CephFS MDS / DRBD Users Guide. A lead wanting citable architecture pages should re-fetch those three guides' Concepts/architecture chapters and swap in the canonical URLs; the conclusion is unlikely to flip — each system genuinely owns its op path — but the URLs above are entry-point rather than in-depth-page citations, and that limitation is owned here rather than hidden.

2. *The library verdict is a fit verdict, not a capability verdict.* §3.2 argues etcd/raft/v3 *permits* Camp A's invariants more naturally and hashicorp/raft *fits* Camp B more ergonomically. A determined team could implement payload-before-reference + refuse-to-campaign as glue above hashicorp/raft's FSM — a specialist audit (Agents 1–6 territory) should rule on whether that glue preserves the invariants under every crash interleaving or merely appears to. Until that proof exists, the recommendation (etcd for MVP) stands on *statability*, not on impossibility of the alternative.

3. *FUSE cost is bounded but unmeasured.* §3.1 accepts FUSE overhead (round-trip, cache discipline, stall-on-failure) as priced by Camp A's qualification gates. No benchmark was run for this reconciliation; if qualification hardware cannot meet §11 (1,000 quorum write+fsync/s, p99 ≤25 ms), the honest response is to renegotiate the SLO, not to drift back to a watcher path that cannot meet the correctness contract at any speed.

4. *Refactoring risk is asymmetric and acknowledged.* Camp B's failure-state taxonomy, quarantine, and POSIX-apply discipline are adopted here as sub-mechanisms, but their original wording assumes a watcher journal and per-directory epochs. Mapping them onto Raft term/index + chunk receipts (candidate/CATCHING_UP vote guards, forced-promotion sequencing, tiered async contracts) is real work that this document scopes but does not complete — re-scoped sheets (§4) must do it without reintroducing the superseded data path.

5. *No spec files were edited.* Per tasking, this file only was written. All banners and D-001 are proposals for the lead to apply; until the lead applies §4 banners and appends D-001, the speaking-ship risk remains that an implementer reads an archived file as live spec. Prompt application of the banners is therefore part of closing the fork, not an administrative afterthought.
