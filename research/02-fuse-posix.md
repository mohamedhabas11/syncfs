## 1. FUSE kernel/userspace protocol and VFS mount

### Verdict: ✅ DIRECTION MATCHES — Underspecified at the VFS boundary, not wrong

The spec presents FUSE as the synchronous interception point ("Translate Linux FUSE requests and errors; forward locks; use strict cache policy", `.spec/technical_spec.md` §5.2; `docs/architecture.md` write path diagram FUSE → leader → quorum → success). That matches the kernel model. The missing detail is mount-time negotiation, `fusectl` abort, and the documented FUSE deadlock scenarios — all of which M3-01/M3-03 will hit immediately.

**Analysis.** Nothing in §1 refutes the unified baseline. The FUSE interception model *is* the kernel-documented userspace-filesystem model: kernel threads sleep on `req->waitq` until userspace replies. Camp B's native-dir watcher has no equivalent hook in this documentation — consistent with D-001 §2 Q1. For M3, the audit-relevant underspecification is at the mount boundary: which kernel capabilities are negotiated (`CAP_*`), which mount flags (`default_permissions`, `allow_other`), and which abort path (`fusectl` write vs `umount -f` vs daemon kill). Those choices directly affect whether the suspended-process and `ENOTCONN` claims (§6) are even expressible. M3-01 must pin them; the spec currently leaves them implicit.

## 2. FUSE caching model — attr TTL, entry TTL, invalidation, Forget, direct vs cached I/O

### Verdict: ✅ Spec's cache posture maps to the documented API — Negative cache + sub-caches + Forget unnamed

`.spec/technical_spec.md` §8.3: *"Minimal kernel FUSE caching with zero/very short metadata TTL and direct I/O for mutable file data in the initial release. This prevents a paused or disconnected mount process from allowing the kernel to serve an expired page."* `docs/architecture.md` L125–129: *"it uses FUSE direct I/O for mutable data and zero/short kernel metadata TTLs."* That is the documented toolset for strictness. The gaps are the *other* kernel caches the spec never names (negative dentries, symlink page-cache, ACL cache, readdir cache) and the `Forget` / `NOTIFY_*` lifecycle.

**Analysis.** The spec's cache posture is the kernel-documented strict posture, and go-fuse/v2 exposes every knob the posture requires (`EntryTimeout`, `AttrTimeout`, `NegativeTimeout`, `FOPEN_DIRECT_IO`, `NotifyContent/NotifyEntry/NotifyDelete`, `ExplicitDataCacheControl`, `EnableSymlinkCaching`, `EnableAcl`). The audit concern is not that the knobs don't exist — they do — but that the spec names only the first two and leaves the rest to implementation guesswork. With TTL=0 and `FOPEN_DIRECT_IO` on every mutable open, most cache hazards collapse, *except* negative dentries (if the implementer leaves `NegativeTimeout` at a nonzero default), symlink page-cache (if `EnableSymlinkCaching` is ever set), ACL cache (if `EnableAcl` is ever set), and readdir cache (if `FOPEN_CACHE_DIR` is set). M3-01 should pin all five to the strict-safe value rather than relying on defaults. This is a precision fix, not a baseline challenge (D-001 compatible).

## 3. go-fuse/v2 features — locks, handles, attr validity, writeback, direct I/O, NOT supported

### Verdict: ✅ Selection is sound — Writeback/direct-I/O knobs need go-fuse-accurate naming; "NOT supported" list needs one correction

`.spec/technical_spec.md` §6 selects `github.com/hanwen/go-fuse/v2` for "Go-native FUSE protocol coverage, lock forwarding, explicit cache controls, and direct Linux focus." That summary is accurate against the library's own docs. The issues are (a) there is no `EnableWritebackCache` field in go-fuse/v2 `MountOptions` to name (writeback is negotiated via capabilities — spec/architecture wording must match go-fuse reality), and (b) the spec's `mmap` exclusion over-states what `EOPNOTSUPP` achieves.

## 4. POSIX lock semantics — flock vs fcntl vs OFD, ownership, release, blocking, FUSE forwarding, upgrade/downgrade, deadlock

### Verdict: ⚠️ COLLAPSED MODEL — Topology (Raft-ordered) is right; the three POSIX families are conflated

`.spec/technical_spec.md` §8.3: *"flock and POSIX range locks are state-machine records keyed by inode, owner session, process lock owner, range, and lock mode. Blocking locks wait on the leader; nonblocking locks return EAGAIN. Session expiry releases its locks in Raft order and emits invalidations."* `docs/compatibility.md` L18: *"Cluster-coherent `flock` and POSIX byte-range locks; lock ownership is tied to the client session and released after session expiry."*

That paragraph correctly places lock authority in the Raft leader (D-001 baseline: fencing token = Raft term/index, §8.4). It omits every hard part: the three lock families have *different* owners, *different* release triggers, and *different* deadlock/upgrading rules, and FUSE forwards them through *different* opcodes/flags. A state machine keyed by `(inode, session, process owner, range, mode)` cannot express the differences without more fields and more transition rules.

## 8. Gaps — what the spec does not yet specify

### G-1. Lock manager design missing (wait queues, deadlock, session expiry ordering) — CRITICAL

**Spec state:** §8.3 two sentences + compatibility L18 + tasks M2-06/M3-02 name the words (`lock state`, `lock forwarding`, `EAGAIN`). No wait-queue, fairness, deadlock, upgrade, `Getlk` information, `Release`-vs-`F_UNLCK` split, or expiry-vs-inflight ordering.

**Why it blocks M3:** A Raft-ordered lock table without wait queues cannot implement blocking `F_SETLKW`/`flock` at all; with naive queues it will wedge or be unfair. The kernel evidence (§4) shows three families need three ownership keys and two deadlock policies.

**Missing pieces (each needs a state-machine rule):**
1. **Ownership keys.** `flock` → open-file-description ID (survives `dup`/`fork`, dies on last close); POSIX `F_SETLK` → `(session, pid)` (dies on *any* close of that file by that pid, not inherited by `fork`); OFD → OFD ID (fork-inherited, last-close release). FUSE provides the raw material: `LkIn.{NodeId, Fh, LockOwner}`, `flags & FUSE_LK_FLOCK`, `FileLock.{Type, Start, Len, PID}`. Spec's `(inode, session, process owner)` covers only family 2.
2. **Wait queues + fairness.** Blocking `Setlkw` must enqueue per-inode (and per-range overlap) with FIFO or priority order, Raft-ordered grant on release, `EINTR` on signal/interrupt (`fuse.Context` cancellation → `EINTR` per go-fuse Interrupts docs), and `F_GETLK` snapshot of the *current* holder (may be stale by the time the caller reads it — `fcntl_locking(2)` warns explicitly).
3. **Deadlock detection policy.** `fcntl(F_SETLKW)` (POSIX family) → kernel does wait-graph detection + `EDEADLK`. `flock` and OFD → *no* detection (block forever). Distributed case: wait graph spans hosts/sessions — either (a) no detection (document wedging + operator metrics), (b) leader-side wait-graph cycle detection with `EDEADLK` + false-positive/negative tolerance (kernel limits search to 10 steps), or (c) timeout → `EAGAIN`/`ETIMEDOUT`. Spec must pick; "blocking waits on the leader" is not a deadlock policy.
4. **Upgrade/downgrade + partial-range split/coalesce.** `flock` conversion is non-atomic locally; `fcntl` conversion splits/shrinks/coalesces interval lists. Raft state machine may make both atomic (stronger, permissible) but must state it and must maintain an *interval set*, not a single `(range, mode)` row. `l_len==0` = to-EOF; negative `l_len` (Linux ≥2.4.21) = backwards range.
5. **Open-mode gating.** Read lock requires fd open for reading; write lock requires open for writing (`fcntl_locking(2)`, `EBADF` otherwise). FUSE `OpenIn.Flags` + `FileHandle` must be checked before grant.
6. **Release paths.** Three distinct triggers: explicit `LOCK_UN`/`F_UNLCK` (via `Setlk`), `Release` with `FUSE_RELEASE_FLOCK_UNLOCK` (flock last-close), session expiry (spec's "releases in Raft order"). Order among them matters: explicit unlock during inflight `Setlkw`, `Release` racing `Setlkw`, expiry racing a newly granted lock.
7. **Session expiry ordering.** "Session expiry releases its locks in Raft order" (§8.3) vs "dead session must expire before conflicting command can proceed" (§8.2 step 6, for leases). Need: expiry is a Raft command (or leader-derived event) ordered *before* the next grant on the same range; in-flight `Setlkw` waiters unblock with `EIO`/`ENOTCONN`/`EINTR` (not `EDEADLK`); `EIO`-until-close rule for I/O on a lock lost to partition (`fcntl_locking(2)` "Lost locks").
8. **Lock-record persistence.** Locks are state-machine records (§8.3) — but are they *snapshot* state or *ephemeral*? If a leader crashes, are held locks restored from snapshot or dropped (forcing re-acquire)? Spec §8.5 snapshot = "metadata checkpoint" — must state lock-table inclusion explicitly.

### G-2. Suspended-process cache safety — Inv.6 over-promises

**Spec state:** Inv.6 ("MUST invalidate before lease expires or on control-conn fail"), §8.3 ("Minimal kernel caching … This prevents a paused or disconnected mount process from allowing the kernel to serve an expired page"), architecture L127–129.

**Reality (kernel evidence §2/§6):** A paused process cannot run invalidation. With TTL=0 + `FOPEN_DIRECT_IO`, pausing → `read`/`lookup`/`getattr` *block* on `req->waitq` (no stale serve) — which is the strict-safe behaviour. But (a) already-faulted `mmap` pages remain readable, (b) control-conn loss is only *observed* by the resumed process, and (c) "before lease expires" cannot be honoured under suspension. The spec's own §8.3 sentence ("must test host suspension") is the correct framing; Inv.6's absoluteness is not.

**Missing:** Definition of the test that distinguishes *block* (correct under pause) from *serve-stale* (incorrect) from *fail-fast `ENOTCONN`* (correct only after `fusectl` abort). Also per-file `mmap` exception (faulted pages) and the dead-session-expiry-before-proceed (§8.2 step 6) interaction: a suspended holder blocks the leader's lease-revocation path until session expiry — the commit latency SLO (§11) needs a bound tied to session-expiry timeout, not just `p99`.

### G-3. Dentry / negative cache — the stale-`ENOENT` window

**Spec state:** Not mentioned. Positive TTL is noted; negative TTL, `d_revalidate`, `INC_EPOCH`, `inval_wq` are not.

**Reality:** `fuse-caches.html` §5.6: lookups failing with `-ENOENT` set expiry to 0 (kernel will re-`LOOKUP` on next use *if* timeout is 0). go-fuse caches failed lookups iff the implementer sets an entry timeout on the `ENOENT` path (`NegativeTimeout`). With the mount-level default (1s) or any nonzero `NegativeTimeout`, a Raft-committed `create` can be hidden for that window — a *knowingly stale read* in the strict sense.

**Missing:** Pin `NegativeTimeout = 0` (and per-call `ENOENT` timeout 0), state `d_revalidate` behaviour (expired → `FUSE_LOOKUP`; generation mismatch → `FORGET` + invalidate), and decide `inval_wq` (default disabled = lazy prune only; enabling requires the `inval_wq >= 5` module parameter and changes memory behaviour). Also: `Lookup` on `EEXIST` (create race) sets expiry 0 — the §8.2 step-7 idempotency path ("duplicate returns retained result") must not cache a stale positive entry after an `EEXIST` collision.

### G-4. fsyncdir ordering — file durability ≠ name durability

**Spec state:** Compatibility L16 lumps all durability; §3 Accept-5 names `fsyncdir` once; §8.3 never mentions `Fsyncdir`.

**Reality (`fsync(2)`):** `fsync(file)` does not flush the directory entry; an explicit `fsync` on a directory fd is required. For `create`/`rename`/`link`/`unlink`/`mkdir`/`rmdir`, the durable-name guarantee needs: (1) Raft commit (already required), **plus** (2) an `Fsyncdir` quorum commit for *each* affected parent (for `rename`: both source and target parents, or a single command that already covers both — spec's "one command even when it changes two parent directories" *is* the (1) part, but the `Fsyncdir` quorum mapping for that command must be stated). For `fdatasync`, size metadata (`ftruncate`) is in-scope; `atime`/`mtime` are not — spec must state whether it persists them anyway.

**Missing:** `Fsyncdir` quorum rule per command (table: command → parents to fsyncdir-quorum), `Datasync` flag handling in go-fuse `Fsync(ctx, flags)`, `Flush` (close-time) must **not** be a quorum commit, and `fsync` error reporting (`EIO`/`ENOSPC`) for sync-time failures (including write-back errors reported to all open fds since Linux 4.13 — `fsync(2)`).

### G-5. xattr / ACL gaps in the state machine — unrepresentable as written

**Spec state:** §7.3 `Inode{Xattrs map[string][]byte}`; §7.4 `SetXattr`/`SetACL` commands; compatibility L21 "planned", "unsupported namespaces fail explicitly"; §7.4 lists `LockGrant`/`LockRelease`/`VolumeConfig`/`MembershipPlan` among commands (not all POSIX mutations — no `SetAcl` decomposition, no `Fsyncdir` command).

**Reality (`xattr(7)`, `acl(5)`, `fuse-caches.html` §5.4):** Namespaces (`user`/`system`/`trusted`/`security`) have different auth and storage. `user.*` only on regular files/directories, gated by file perms; `system.posix_acl_*` encode access + default ACLs with mask correspondence that *is* the mode bits. Default ACL inheritance + `mode & ~umask` masking. Go-fuse knobs: `DisableXAttrs`, `EnableAcl` (`CAP_POSIX_ACL`), `IgnoreSecurityLabels`.

**Missing:**
- Representation: `map[string][]byte` cannot hold access/default ACLs with uniqueness constraints (`ACL_MASK` required iff extended entries exist; `ACL_USER`/`ACL_GROUP` qualifiers unique). Needs a first-class `AccessACL`/`DefaultACL` record + `ACL_MASK` computation.
- Coupling: `SetAttr(mode)` ↔ `SetXattr(ACL)` must atomically update mode-bits ↔ ACL-entries (the `acl(5)` correspondence). §7.4 `SetAttr`/`SetXattr`/`SetACL` as three separate commands need interaction rules (e.g., `chmod` updates mask; `setfacl` updates group bits; `setfacl` on file without exec bits clears `S_ISGID` — `SETXATTR_ACL_KILL_SGID`).
- Commands: no `Fsyncdir`, no `CopyFileRange`, no `Allocate`, no `Tmpfile` command — yet go-fuse surfaces all of them. Either add commands or record `EOPNOTSUPP` mappings.
- Errnos: `ENODATA` (missing attr), `ENOTSUP`/`EOPNOTSUPP` (namespace), `EPERM` (trusted/security without caps), `EACCES` (user.* without perms), `ENAMETOOLONG`/`E2BIG` (255B name / 64KiB value caps).

### G-6. Symlink target size (and loop handling)

**Spec state:** §7.3 comment "bounded by Linux PATH_MAX".

**Reality:** `symlink(2)` `ENAMETOOLONG` for too-long target; `inode(7)` `st_size` = `len(target)` (no NUL); `symlink(7)` target is interpreted at runtime with `..` relative to link location; kernel enforces `ELOOP` (40 dereferences on Linux) — kernel-side, not server-side, but `Readlink` must return verbatim target (including dangling/absolute/cross-directory forms). POSIX `PATH_MAX` minimum is 1024; Linux `PATH_MAX` is 4096.

**Missing:** Numeric cap (4096) + `ENAMETOOLONG` mapping in `Symlink`/`Readlink`/`Lookup` (target longer than cap must fail at *create*, not at *resolution*), fixed mode `S_IFLNK|0777`, `st_size` rule, and that symlink xattrs (`l*` family) operate on the link itself (`symlink(7)` "do not follow" list: `lchown/lgetxattr/llistxattr/lremovexattr/lsetxattr/lstat/readlink/rename/rmdir/unlink`).

### G-7. Hardlink open-file semantics (distributed lifetime)

**Spec state:** Compatibility L20 correct sentence; §7.3 `LinkCount` no lifetime rule; no `openFiles`/`forgetRefs`/`Release` accounting.

**Reality (`unlink(2)`, `open(2)`, go-fuse `Forget`):** Last-link unlink retains inode until last `close`; fd unaffected by later `rename`/`unlink`; `dup`/`fork` share the open file description (offset + status flags shared); `Forget` is kernel-dentry accounting with no I/O allowed.

**Missing:** Distributed rule: inode retained iff `LinkCount > 0` **or** `openHandles > 0` **or** `forgetRefs > 0` (go-fuse `nodeEntry` open file count + `Generation` reuse rules). Writes/`Fsync`/`Setattr`/`Getlk` via a handle for a `LinkCount==0` inode must still work. `LinkCount` decrements on `Unlink` even when retained; final `Release` + `Forget` triggers the *actual* chunk-GC eligibility (§8.5: "no valid client read lease can reference it" — must add "no open handle can reference it"). `Generation` must not be reused while any handle is open (go-fuse `StableAttr.Gen` discipline), else a new `Lookup` aliases an old handle.

### G-8. O_DIRECT exclusion correctness (errno + mmap enforcement + terminology)

**Spec state:** Compatibility L33 "`O_DIRECT` `EOPNOTSUPP` in strict mode"; §2 non-goal "Strict writable shared mmap, O_DIRECT …"; §8.3 "direct I/O for mutable file data".

**Reality (`open(2)`, `mmap(2)`, `statx(2)`):** Client `open(O_DIRECT)` unsupported → `EINVAL` (not `EOPNOTSUPP`); `EOPNOTSUPP` is for `O_TMPFILE`. Client `O_DIRECT` has alignment (`STATX_DIOALIGN` since 6.1; `stx_dio_*_align == 0` ⇔ unsupported) and `fork`/`mmap` mixing hazards. Writable shared `mmap` exclusion cannot be enforced by returning `EOPNOTSUPP` from `mmap()` (no FUSE opcode for `mmap`); enforcement is via open flags, `CAP_DIRECT_IO_ALLOW_MMAP`, and page-fault behaviour.

**Missing:** (a) Disambiguate the two "direct I/O" meanings in every occurrence (§8.3 server-driven vs compatibility client-flag). (b) Fix errno to `EINVAL` for client `O_DIRECT` (or justify `EOPNOTSUPP` as a SyncFS extension and pin it). (c) State `statx` `DIOALIGN` reporting (`0` for strict mounts). (d) For mmap: state the enforcement point and the allowed subset (e.g., read-only `MAP_PRIVATE` allowed via `FUSE_READ` faults; `MAP_SHARED`+`PROT_WRITE` → `EACCES`/`EIO` at fault, or never faultable because `CapDirectIoAllowMmap` is off and every write faults through userspace quorum). Currently "Shared writable mmap `EOPNOTSUPP`" names an errno that cannot be returned at the named call.

**C-15 — `docs/architecture.md` L185 + `.spec/technical_spec.md` §4 Inv.6 / §8.3 — Abort mechanism + suspension wording**
- *Location:* architecture failure-model row "Mount process failure"; Inv.6; §8.3 tests.
- *Current (arch L185):* "The kernel FUSE connection is aborted; callers receive an error rather than silently using stale data. Systemd restarts and remounts the client."
- *Proposed replacement (arch):* "Mount-process failure: pending FUSE requests never reply and their threads block (observable as `waiting > 0` in `/sys/fs/fuse/connections/<id>/waiting`). ## 10. Honesty note

**What this report does well and where it could be wrong.**

1. *Method boundary.* Evidence is primary-source only (kernel docs, go-fuse repo/pkg docs + raw source, Linux man-pages 6.19). No benchmark was run, no code was compiled, no mount was performed. Verdicts about "matches go-fuse API" mean the API *surface* exists as described; they do not mean the spec's Raft quorum design is performant (§11 gates are Agents-plan territory, not this domain's). Kernel-doc excerpts are from `docs.kernel.org` 7.4.0-rc1 rendering; the `fuse.html`/`fuse-caches.html` split may drift across kernel reorgs. URLs are pinned to the documents fetched; `raw.githubusercontent.com/.../master/...` URLs are branch-relative and will move with go-fuse releases — `pkg.go.dev` `v2.12.1` anchors are the stable cache for the same facts.

2. *Lock-manager depth (Gap G-1).*
`fcntl_locking(2)`'s deadlock-detection BUGS (false pos/neg, 10-step depth limit) and the distributed wait-graph problem are stated from the man page, not from a deployed distributed-lock proof. The report recommends the Raft-ordered *topology* (D-001-consistent) but does not prove that a particular wait-graph algorithm meets the §11 `p99` SLOs under contention. Whether SyncFS chooses `EDEADLK` detection or block-forever for `F_SETLKW` is a product choice the spec must make — the man page constrains the menu, it does not pick the item.

3. *go-fuse capability negotiation.*
The writeback-cache finding (no `EnableWritebackCache` mount field; capability-gated via `ExtraCapabilities`/`DisabledCapabilities`/`InitHandler`) is based on the `fuse/api.go` `MountOptions` struct fetched at `master`/`v2.12.1`. If a later go-fuse adds a convenience boolean, C-06 becomes a simplification, not a correctness fix — the *capability-disabled* requirement stands regardless. Similarly, `OFD` lock forwarding in newer kernels (`F_OFD_*` since 3.15) is described from the `man`-page semantics + `FUSE_LK_FLOCK` flag evidence; the exact `LkIn` encoding of OFD vs POSIX across kernels was not traced kernel-source-wide (would require `fs/fuse/file.c` in-tree). The gap stands either way: spec must branch on it.

4. *Errno contestability.*
`EHOSTDOWN`/`ESTALE`/`EOPNOTSUPP`-for-`O_DIRECT` are flagged as *questionable/wrong* relative to `man 2` precedent. A team could deliberately retain them as documented SyncFS extensions (the report says so for `EHOSTDOWN`). What cannot be retained without contradicting the man pages is the *claim* that they are the standard filesystem errnos — they are not. Similarly, `EACCES`-vs-`EAGAIN` for `F_SETLK` is a Linux-local vs POSIX-portable choice; the report pins the POSIX-portable statement and lets the hotspot be explicit.

5. *Scope limit — no FUSE protocol deep-dive.*
This audit covers mount, caching, locks, handles, error mapping, and POSIX file semantics at the *syscall* level. It does not audit the wire protocol (`fuse_opcode` table, `InitIn/Out` version negotiation beyond caps, `ReadIn/WriteIn` windowing, `InterruptIn`, `NotifyRetrieve/StoreCache`, `IoctlIn`, `CopyFileRange` semantics) or the quorum protocol (§8.2 CQRS/lifecycle), which belong to other domain agents. Findings that touch `Forget`, `INC_EPOCH`, `PruneNotify`, or `Datasync` are raised here only where the *POSIX* consequence (stale read, durability, errno) lives at the FUSE boundary.

6. *No D-001 challenge is a finding, not a hedge.*
The baseline (FUSE + `etcd/raft/v3` + QUIC, Raft term/index fencing, userspace lease cache + kernel TTL≈0 + `FOPEN_DIRECT_IO`, adopted taxonomy/quarantine/POSIX-apply) is fully compatible with every primary source fetched. The eight gaps are spec-precision gaps *within* that baseline. Reopening a watcher mutation path, `hashicorp/raft` MVP selection, or epoch fencing for strict scope would require revisiting 07 §3.1's proof and the north-star contract (07 §5 Consequences) — nothing in this domain's evidence supports such a revisit.
