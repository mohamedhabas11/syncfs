| 6.2 | What if the lease holder ignores revocation? SyncFS requires ack-or-expiry but defines neither the bounded wait nor the expiry | Tech §8.2 step 6 "A live lease holder must invalidate and acknowledge; a dead session must expire before the command can proceed.", §8.3 step 3 "waits for each live lease holder to acknowledge revocation or time out" | Gluster https://docs.gluster.org/en/main/release-notes/3.9.0 ; CephFS recall (above) | Gluster 3.9: "Lock revocation feature … Adds option to strip clients of entry/inode locks after N seconds" ; "Adds option to clear ALL locks should the revocation threshold get hit" ; Gluster defaults: "`features.locks-revocation-secs 0`", "`features.lease-lock-recall-timeout 60`" | **UNSPECIFIED — must be fixed before M2-06.** "Expire" needs: (a) a maximum ack wait (e.g. 2 s) after which the leader proceeds anyway and fences the holder by Raft term/index (the holder's next read must fail); (b) a session-liveness detector (QUIC idle timeout? heartbeat?); (c) fencing-token semantics (what does the mount do if it gets the ack *after* the deadline?). Without (a), a hung mount deadlocks all conflicting writes. With (a) but without (c), the holder can serve stale data after the deadline. CephFS's answer is a *throttled recall + health warning*, not an unbounded block. |

## 2. Latency and throughput math — explicit budget

### 2.1 Physical floor (etcd's formula, applied twice for SyncFS)

etcd: `minimum = RTT + fdatasync`  
SyncFS §8.2 steps 4–8: `minimum = FUSE + chunk-prep-RTT + chunk-fsync + lease-RTT + Raft-RTT + Raft-fsync + apply-fsync + reply`

Reference numbers used below (all from §1 excerpts):

- LAN RTT (datacenter, 10 GbE, consecutive racks): **0.2–0.5 ms** (etcd: "several hundred microseconds").
- Enterprise NVMe `fdatasync` (small append, PLP): **0.05–0.5 ms typical**, e.g. SmallDatum "51 µs" and KernelInternals "50–500 µs (PCIe 4.0)".
- Consumer NVMe / XFS / `fsync`-instead-of-`fdatasync`: **1.6–9.6 ms** (Tanel Poder 1.6 ms fdatasync / 5.6 ms fsync on XFS/NVMe; Percona 9.6 ms on consumer NVMe; KernelInternals SATA 1–5 ms).
- HDD `fdatasync`: **~10 ms** (etcd).

Assume staged, parallel follower I/O (followers `fdatasync` concurrently, leader waits for the *median* — CockroachDB `L_c` definition).

### 2.2 Latency budget — 4 KiB quorum write (Tech §11: p99 ≤ 25 ms)

Worked example for a 4 KiB write that touches **one** existing 64 KiB chunk (the common Jira/attachment small-write case). The spec's §8.2 step 3 "A write spanning an existing chunk reads and rewrites that one chunk" means the leader must **read 64 KiB locally** before it can stage the new chunk — this read is not in §11's budget at all (Gap G8).

| Phase (spec step) | If strictly sequential (§8.2 as written) | If chunk-prep ∥ Raft-propose is *pipelined* (Architecture as written) | Notes |
|---|---|---|---|
| 0. FUSE → client → leader (RT) | 0.3 ms | 0.3 ms | Kernel→userspace→QUIC→leader. Includes protobuf marshal in Go (`proto.Marshal`). |
| 1. Validate + precondition check (§8.2.1) | 0.2 ms | 0.2 ms | Pebble point-get on inode/dentry. |
| 2. Chunk build: read old 64 KiB (if partial) + CoW + BLAKE3 (§8.2.3) | 0.5 ms (local SSD read) | 0.5 ms | BLAKE3 ~µs. **Missing from §11 budget.** |
| 3. Stage locally: write 64 KiB pack + `fdatasync` (§8.2.4) | 0.3 ms (enterprise) / 3 ms (consumer XFS) | 0.3 ms | One pack `fdatasync`. |
| 4. Stream to 1 follower + follower `fdatasync` + receipt (§8.2.4–5) | 0.3 (RTT) + 0.3 (remote fsync) = 0.6 ms | 0.6 ms, overlaps step 5 | 64 KiB on 10 GbE = 0.05 ms wire. Dominated by fsync. |
| 5. Lease revocation: send + ack (§8.2.6) | 0.3 ms happy / **+2000 ms** if a holder times out | Same | Happy path is concurrent with step 4. Unhappy path is the tail risk. |
| 6. Raft propose → leader WAL `fdatasync` + follower WAL `fdatasync` + majority commit (§8.2.7–8) | 0.3 (RTT) + 0.3 (leader fsync) + 0.3 (follower fsync, parallel) = 0.9 ms | 0.9 ms | Second `L_c`. In CockroachDB terms, `L_c ≈ 0.6 ms` here. |
| 7. Fetch missing chunks (if any) + apply Pebble batch + result record `fdatasync` (§8.2.8) | 0.3 ms (Pebble WAL fsync) | 0.3 ms | **Third fsync** if Pebble is synced per-apply. If Pebble is grouped (Pebble commit pipeline), this is amortized — §11 never says. |
| 8. Invalidate + reply (§8.2.9) | 0.3 ms | 0.3 ms | |
| **Total (mean, enterprise NVMe, no lease wait)** | **~3.9 ms** | **~3.3 ms** (lease ∥ chunk) | |
| **Total (consumer NVMe / XFS, `fsync` not `fdatasync`, 3× ~2 ms)** | **~9–10 ms mean** | ~8.5 ms | Still under 25 ms *mean*, but the **p99 tail** (fsync at 9 ms each → 27 ms for three) **exceeds 25 ms by itself**. |
| **Total (HDD, 10 ms fsync × 3)** | **~32 ms** | ~31 ms | **Impossible.** §11's "NVMe that honors flushes" excludes HDD, but the spec must say so in the qualification gate, not just in prose. |

**Verdict on 25 ms p99:** *Plausible as an engineering estimate on the named enterprise-NVMe profile with `fdatasync`, a dedicated WAL/pack file (not XFS journal), no lease wait, and Pebble group-commit. Not plausible as a universal claim.* The budget has ~21 ms of headroom to absorb queueing, but a single lease-timeout tail, a single consumer-NVMe 9 ms fsync tail × 2, or a compaction stall consumes all of it. The target is **not aspirational** — it is inside the physical floor — but it is **unproven**: no measurement exists (M5-01 has not run), and the spec's own "reference hardware" sentence ("NVMe that honors flushes") does not pin enough to reproduce the number.

### 2.3 Throughput math — 1000 ops/s

- Inter-arrival at 1000 ops/s = **1.0 ms**.
- Group-commit window *W* = 2 ms → expected batch *B ≈ λ·W = 2* (at steady state, arrival process permitting). Each batch pays one Raft WAL `fdatasync` and (if grouped) one Pebble `fdatasync`.
- Little's law: concurrency `N = λ·L = 1000 × 0.004 (mean) = 4` in-flight on average; `N_p99 = 1000 × 0.025 = 25` at the p99 target. The leader must sustain **25-deep pipelining** (concurrent chunk-preps + Raft proposes) without unbounded queue growth — exactly what M5-01's "no unbounded queue growth" gate must prove.
- Fsync capacity: serial fsync at 0.3 ms → 3,333 fsync/s ceiling. At *B = 2*, each op costs 0.5 fsync (Raft) + 1.0 fsync (chunk) + 0.5 fsync (Pebble) ≈ 2.0 fsyncs/op → 2,000 fsync/s at 1000 ops/s. This is **below** the 3,333 ceiling but with only 1.7× headroom. At consumer-XFS 2 ms fsync (500 fsync/s ceiling), 1000 ops/s is **impossible** serially — group commit would need *B ≥ 12* (a 12 ms window) to fit. The spec's fixed "0–5 ms (default 2 ms)" window is therefore **not universally sufficient**; it must be adaptive to measured fsync latency (or the qualification gate must fix the hardware).
- Bandwidth: 1000 ops/s × 64 KiB CoW = **64 MB/s** payload + ~10 MB/s metadata/WAL — trivial for 10 GbE (1.25 GB/s) and NVMe (several GB/s). Bandwidth is not the bottleneck; fsync count is.
- CPU: 1000 × (BLAKE3 + protobuf + Pebble batch) is trivial for Go at these sizes. The bottleneck is the three serial fsyncs, not CPU.

**Verdict:** 1000 ops/s is *throughput-plausible* on enterprise NVMe with grouping; the spec's mechanism (group commit + QUIC pipelining) is the right one (TigerBeetle, etcd, CockroachDB, Pebble all agree). But §11 presents it as a measured gate when no measurement exists — it is an **estimate**, not a result.

### 2.4 Cache-hit read p99 ≤ 2 ms — what it actually comprises

Tech §8.3 defines two layers: userspace cache (lease-guarded) + FUSE kernel cache (zero/short TTL, direct I/O for mutable data).

| Path | Cost (mean) | Included in 2 ms? |
|---|---|---|
| FUSE `READ` → userspace → map hit → copy → reply | 0.2–0.5 ms | Yes — this alone is ~25% of the budget. |
| Lease-validity check (local map, no RPC) | ~0.01 ms | Yes. |
| Byte copy (4 KiB) + protobuf | ~0.05 ms | Yes. |
| **Warm hit total** | **~0.3–0.6 ms** | **Within 2 ms.** |
| Cold hit (lease valid, chunk not in mount cache → QUIC fetch + verify + disk read) | 1.5–4 ms + fsync-tail | **Exceeds 2 ms.** Must be excluded from "cache-hit" or the target fails. |
| Revalidation (lease expired → ReadIndex through Raft) | 1 RTT + `L_c` ≈ 1–2 ms | Borderline. Must be excluded — §8.3 says "Fresh reads use a Raft ReadIndex barrier or a valid lease." A ReadIndex *is* a quorum RPC. |
| Mutable file data with direct I/O (§8.3) | One chunk fetch every read | **Not a cache hit at all.** The 2 ms claim only holds for *immutable* or already-pinned files. |

CephFS makes the same point operationally: the MDS cache exists "to improve metadata access latency," but recall is throttled and a slow client triggers "failing to respond to cache pressure" — i.e., cache gains are *eventually* paid back as recall stalls. SyncFS's claim must be reworded as: *"warm userspace metadata + pinned immutable chunk, lease valid, no network, no ReadIndex; cold/mutable/ReadIndex reads excluded."* As written, §11's "cache-hit strict reads" is **unfalsifiable** (no definition of hit).

### 2.5 Create/write/rename 4 KiB at 500 ops/s p99 ≤ 30 ms

Same budget as §2.2 plus directory-entry + inode-create Raft work (rename touches two dentries — §8.2 "Rename is one command even when it changes two parent directories" — so one Raft entry, not two). The 5 ms extra headroom vs. §2.2 (30 ms vs 25 ms) is directionally right (directory lock + two-parent precondition). Plausibility is the same as §2.2: plausible on enterprise NVMe, not on consumer XFS at tail.

## 3. Gaps — what the spec leaves undefined

**G1 — Idempotency result retention bound is undefined (CRITICAL).**  
§4.7 "The leader MUST durably retain a bounded result record" and §8.2 step 2 "A duplicate returns its retained result." No bound (count? bytes? time? Raft-index distance?), no eviction rule, no GC interaction with snapshots (§8.5), no behavior for an evicted ID, no storage location (Pebble? separate table? what key?). *Why it matters:* without a bound, either (a) unbounded growth breaks disk-full (§10), or (b) a silent eviction reintroduces double-apply (see row 2.4). M2-05 cannot be implemented or tested. TigerBeetle's answer (never evict) is explicit; industry dedup (24 h) is explicit. SyncFS must pick.

**G2 — Ambiguous-operation deadline is undefined (CRITICAL).**  
§8.2: "If a leader cannot prove the outcome before the request deadline, FUSE receives an I/O error." No value, no owner (client? leader? mount?), no clock (monotonic? Raft term?), no `GetOperation` semantics (ReadIndex? leader-local? Raft proposal?), no FUSE errno mapping (`EIO` vs `ESTALE` vs `EAGAIN` — the difference between "retry the syscall" and "fail the process"). §10 repeats the vagueness: "If unresolved by deadline, report an error rather than guessing." M3-03's "reconnect/status lookup" task needs a concrete number and errno table or it will invent them.

**G3 — Revision vs. RaftIndex dual clock confusion (HIGH).**  
§7.1 defines `_type Version struct { RaftIndex uint64; Revision uint32 }_` with the note "RaftIndex establishes the total order … Revision permits more than one logical object update inside a single command without inventing a second global clock." This is contradictory: if `Revision` is not a global clock, what orders it? And §7.4 `Preconditions []ExpectedVersion` — does a precondition compare `RaftIndex`, `Revision`, or both? A `uint32` Revision wraps at 4B updates (≈ 46 days at 1000 ops/s). etcd solved this with a single 64-bit `revision` (monotonic, per-key `mod_revision` + store `revision`). SyncFS has two clocks and no rule for which the FUSE layer, the lease generation (§8.3 "records the inode/directory generation"), or `ExpectedVersion` actually uses. Every precondition check in M2-03 depends on this.

**G4 — Precondition model detail missing (HIGH).**  
§7.4 `Preconditions []ExpectedVersion`, §7.4 prose "An apply either changes every listed logical record or changes none. Preconditions prevent accidental lost updates." No `ExpectedVersion` struct definition is given (only referenced). Missing: what is compared (full `Version`? just `RaftIndex`? inode `Version` vs dentry parent generation?), what happens on mismatch (return `CONFLICT` to FUSE as what errno?), how `O_CREAT|O_EXCL` and `rename`'s two-parent case encode their preconditions, whether `LockGrant` preconditions participate. M2-03 "precondition, and operation-result records" cannot be written without this.

**G5 — Group commit implementer missing (HIGH).**  
§11 "short, configurable group commit bounded to 0–5 ms (default target: 2 ms)" and Architecture "The leader combines independent requests." Missing: who groups (volume leader? Raft driver? Pebble wrapper?), over what set (Raft entries only, or chunk writes + Raft + Pebble?), batching condition (timer only, count only, both?), max batch (size? count?), admission control / backpressure (what happens when the input queue is full — `EAGAIN`? block?), fairness across mounts, interaction with `fdatasync` vs `fsync`. Pebble's model ("Each group is assigned a 'leader' [batch] … written atomically to the WAL by the leader thread") is a proven template; SyncFS must adopt or explicitly diverge. Without this, M5-01's throughput number is unrepeatable (different grouping → different fsync count → different p99).

**G6 — Lease revocation: bounded wait, expiry semantics, and fencing undefined (HIGH).**  
§8.2 step 6 + §8.3 step 3 require "invalidate and acknowledge; a dead session must expire before the command can proceed" / "waits for … acknowledge revocation or time out." No timeout value, no session-dead detection (QUIC idle? heartbeat interval?), no fencing token (Raft term? `RaftIndex`? lease `LeaseID` monotonic?), no behavior when the ack arrives *after* the leader proceeded (does the mount drop the cache entry and ack late, or does it serve stale until its next RPC?). Gluster (`locks-revocation-secs`, `lease-lock-recall-timeout 60`) and CephFS (recall throttle + health warning) both define these. SyncFS must define: ack timeout (suggested 2000 ms ≪ 25 ms p99 tail allowance?), expiry detection, and a Raft-term fencing check on every cached read.

**G7 — Payload-before-reference garbage: epoch/GC undefined (MEDIUM).**  
§8.5 "mark-and-sweep with a persisted generation" — generation of *what*? Raft term? Snapshot index? Wall-clock epoch? Who advances it? What bounds staging/ growth under repeated crash-after-receipts? §10 says chunks "remain unreachable garbage" — but §8.5's collectible predicate ("no retained metadata snapshot, committed manifest, in-flight operation, or valid client read lease can reference it") requires the GC to know about *in-flight* operations, which requires the operation table from G1 to exist. Chicken-and-egg unless G1 is fixed first.

**G8 — 64 KiB read-modify-write cost is missing from the perf budget (MEDIUM).**  
§8.2 step 3 "A write spanning an existing chunk reads and rewrites that one chunk" — a 4 KiB partial write pays a 64 KiB read (leader-local SSD if cached, follower fetch if not) + rewrite + double write-amplification in the latency *and* throughput math. §11's 4 KiB targets implicitly assume full-chunk-aligned writes or cache-resident chunks. The benchmark harness (M5-01) must specify chunk-aligned vs random-partial-write workloads, or the 1000 ops/s number is meaningless.

**G9 — Chunk-prep vs Raft ordering contradicts itself (MEDIUM).**  
Architecture: "Chunk upload and Raft replication are pipelined on separate QUIC streams, so a large transfer does not block metadata." §8.2 step 7: "Propose exactly one WriteRanges command [after] receipts." True consensus pipelining (CockroachDB async-consensus / propose-then-prove) would propose *before* receipts and prove at commit; transport pipelining (separate streams) only prevents network HOL. The spec uses one word for both. This matters for large writes: a 10 MB write's chunk-prep (10 MB × majority, fanned out) serialized before propose adds ~10 ms (10 GbE) + fsyncs to the critical path; pipelined (propose metadata early, stream chunks concurrently, barrier at apply) would hide it. §11 never says which policy is intended for bulk chunks.

**G10 — Protobuf size limits vs Raft entry bounds (LOW).**  
§8.1 "Protobuf length prefixes have strict maximum sizes." No numbers. Raft entries must be bounded (etcd's `max-request-bytes` default is 1.5 MB, but SyncFS's `Command` carries `PreparedChunks` receipts + `Payload` — a rename touching many dentries or a `WriteRanges` over many chunks can exceed it). M1-02 must set per-message maxima (Raft entry ≤ 256 KiB suggested; chunk stream frame ≤ 1 MiB) and M2-05 must chunk multi-range writes into multiple commands or reject them.

## 4. Concrete corrections proposed (spec patches — *proposed only*, not applied)

**C1 — Protobuf (M1-02).**  
Adopt: `package syncfs.v1;` one `.proto` per top-level message; `buf lint` with `DEFAULT` + `PACKAGE_DIRECTORY_MATCH`; `buf breaking --against '.git#branch=main'` with `use: [PACKAGE]` in CI on every PR; `reserved` on every deleted field/enum; per-message size caps in `buf.yaml` (`max_request_bytes`). Replace `Command.Payload []byte` with a true `oneof` (or rename field to `payload_bytes` and document manual dispatch — do not call a `bytes` field a "protobuf oneof").

**C2 — Idempotency bound (M2-05).**  
Define the result record explicitly. Recommended default (to be pinned before M2-05 starts):

- Key: `OperationID` → value: `{ outcome: COMMITTED|REJECTED, raft_index, result_errno, write_timestamp }`.
- Retention: keep all records with `raft_index > snapshot_index - 1_000_000` **and** `write_timestamp > now - 7 days`; evict only by raft_index (never by wall-clock alone), and only after the snapshot that contains them is durably stored on the evicting node. This ties the dedup window to the snapshot/GC boundary (§8.5), so an evicted ID is provably committed on a majority (snapshot) — a retry after eviction then correctly returns `CONFLICT`-from-precondition (stale `ExpectedVersion`) rather than double-apply, *if* preconditions are checked as `expected == current` (see C4). Document the eviction-then-retry case in §10 as a known at-least-once-after-7-days operator contract ("clients MUST NOT retry an OperationID older than the snapshot horizon; use a new ID").
- In-flight dedup: while an `OperationID` is in-flight, a second `Propose` with the same ID returns `ABORTED` + `RetryInfo` (gRPC-style) rather than a second Raft entry.

**C3 — Ambiguous-operation deadline + FUSE mapping (M3-03).**  
Pin: leader owns a 10 s outcome deadline (monotonic clock, not wall-clock); `GetOperation(OperationID)` is a ReadIndex-backed linearizable read (§8.3) that returns `COMMITTED|REJECTED|UNKNOWN`. FUSE mapping: `COMMITTED` → replay result errno; `REJECTED` → replay errno; `UNKNOWN` after 10 s → `EIO` (must fail the syscall, must not retry silently); control-connection loss during mutation → `ESTALE` (so the application knows to re-validate, matching §8.3's "return an availability error rather than knowingly serve"). Add a table to `docs/compatibility.md`.

**C4 — Dual clock (M2-03).**  
Collapse to **one** clock: `RaftIndex uint64` is the sole total order. Replace `Version.Revision` with `Version.OpSeq uint16` (sequence *within* a command, for multi-object commands) or delete it. `ExpectedVersion` becomes `{ inode_id, expected_raft_index }` (or `{ parent_id, name, expected_raft_index }` for dentries). Lease generation = `RaftIndex` at grant time. Precondition failure = Raft-committed `REJECTED` result (so `GetOperation` can return it) → FUSE `EAGAIN` for `O_EXCL` / `EEXIST` for create, `ESTALE` for stale rename. `uint32` wraparound disappears.

**C5 — Group commit (M2-04/M2-05, §11).**  
Name the owner: **volume leader** (`internal/volume/write.go`, M2-05's file). Grouped unit: one Raft entry batch **and** one Pebble batch (Pebble commit-pipeline leader). Condition: whichever comes first — 2 ms since the first uncommitted propose arrived, **or** 64 entries, **or** 256 KiB total. Backpressure: input queue depth 512 (RPCs beyond that get `EAGAIN` / QUIC `RESOURCE_EXHAUSTED` immediately, never unbounded buffering). Fairness: round-robin by mount session. Add these numbers to §11 so M5-01 is reproducible.

**C6 — Lease revocation (M2-06, §8.2 step 6 / §8.3).**  
Ack timeout **2000 ms** (tunable, profiled in §11; must be ≪ the 25 ms p99 tail budget's lease-wait allowance, and the qualification run must include a slow-holder fault case). Fencing token: `RaftIndex` at revocation; after the deadline the leader proceeds and the mount's *next* cached read must fail with `ESTALE` (the mount checks the fencing token on every hit, not just on revocation messages). Session-dead detection: QUIC `max_idle_timeout 10 s` + 3 s heartbeat; a dead session's leases are *expired*, not "awaited". Every wait is counted in the `lease_invalidation_latency` metric §12.3 already promises.

**C7 — Garbage epoch (M4-01).**  
Generation = `RaftIndex` of the last snapshot installed on that node. A staging chunk is collectible only when `created_raft_index < generation` **and** no in-flight operation references it (requires C2's table). Cap staging growth: if staging exceeds 10% of volume quota, reject new chunk-preps with `ENOSPC` before Raft propose (extends §10 "disk-full").

**C8 — Benchmark workload (M5-01).**  
Define two 4 KiB workloads: (a) chunk-aligned appends (no RMW read), (b) random 4 KiB partial writes (64 KiB RMW). Report both. The 1000 ops/s claim applies to (a); (b) is separately qualified (suggested 500 ops/s). Both must include the `resource` sidecar §11 already requires (CPU, kernel, flush behavior, network, volume size, binary/config). Add `fdatasync`-only + explicit "enterprise NVMe with power-loss protection" to the reference profile — "honors flushes" alone admits consumer drives that cannot meet p99.

**C9 — Pipelining terminology (§8.1/Architecture).**  
Split the word: "transport pipelining (separate QUIC streams, reserved Raft capacity — §8.1)" vs "consensus pipelining (propose-before-receipts, prove-at-commit — *not* in MVP; §8.2 is strictly sequential: receipts → propose → commit → apply)." The Architecture sentence must be reworded accordingly, or §8.2 step 7 must be changed to the CockroachDB async-consensus pattern with the risk it entails (ambiguous intents, read-your-writes stalls). Do not claim both.

**C10 — Read target ( §11).**  
Reword "cache-hit strict reads" as "warm userspace metadata + pinned immutable chunk hits with a valid lease and no network RPC; cold chunk fetches, mutable direct-I/O reads, and ReadIndex revalidations excluded and separately benchmarked."

## 5. Honesty note — proven vs. estimated vs. hypothesized

**Proven (primary-source evidence in §1):**

- Protobuf TLV wire format + add-field/reserve-tag evolution + `buf breaking PACKAGE` is a sound, industry-standard way to version `api/v1` (protobuf.dev, buf.build, protobuf-go).
- 128-bit client-persisted idempotency IDs (TigerBeetle `u128`) are the correct primitive; etcd proves Raft *without* dedup double-applies on retry, so SyncFS *needs* the OperationID layer.
- etcd's physical floor (`RTT + fdatasync`, SSD < 1 ms / HDD ~10 ms) and RocksDB/Pebble's WAL-group-commit model prove that *batching* (not more threads, not bigger chunks) is the lever for fsync-bound throughput.
- JuiceFS's "upload first, then commit" and CockroachDB's one-Raft-entry-per-commit + Pebble apply prove "payload before reference" + "one command per write" is the standard distributed-storage shape.
- CephFS capabilities/leases and Gluster lock-revocation prove lease-cache + bounded recall is the standard coherence pattern — and prove it needs a *bounded* wait.

**Engineering estimates (plausible, not measured for SyncFS):**

- 4 KiB quorum write mean ~3–4 ms and p99 ≤ 25 ms on enterprise NVMe (`fdatasync`, LAN 0.2–0.5 ms, no lease wait, Pebble grouped). The arithmetic in §2.2 fits, but no SyncFS measurement exists. M5-01 is the test.
- 1000 ops/s sustained with a 2 ms group-commit window (≈2 ops/batch, ~2,000 fsync/s vs a ~3,333/s ceiling). Depends critically on the fsync tail of the *actual* qualification drives.
- Cache-hit p99 ≤ 2 ms for warm immutable pinned hits (~0.3–0.6 ms mean). Depends on the C10 definition; without it, the claim is untestable.

**Unproven hypotheses (must not be presented as results):**

- That "0–5 ms (default 2 ms)" is the optimal group-commit window. No sweep exists. The window trades p99 latency directly against fsync amortization; 2 ms is a guess pending M5-01 data.
- That QUIC stream separation alone ("pipelining") will hide bulk-chunk head-of-line effects under the 1000 ops/s mixed workload. Transport HOL is fixed; Raft-propose serialization is not. Requires a mixed small-write + large-upload benchmark that §11 does not define.
- That lease revocation acks will arrive within the p99 budget under load. CephFS/Gluster both document slow-holder stalls; SyncFS has no recall throttle, no ack timeout, and no fault-case benchmark for a slow mount. Until M2-06/M5-01 measures it, the 25 ms p99 is conditional on "no slow lease holder."

**Bottom line:** the *mechanisms* (§8.2's 9 steps, §11's group commit + QUIC pipelining + 64 KiB CoW) are all standard and correctly chosen. The *numbers* (§11's 1000 ops/s / 25 ms / 2 ms) are reasonable first estimates on the named enterprise-NVMe + 10 GbE profile, but they are **hypotheses to be proven by M5-01**, not properties the design already guarantees. The blockers to proving them are G1–G6: without a pinned idempotency bound, a pinned deadline/errno, a single clock, a precondition definition, a named group-commit owner, and a bounded lease wait, the benchmark cannot be run fairly and the double-apply / stale-read / deadlock failure modes cannot be reasoned about.

## 7. Unified-baseline alignment (07 §3.5 / D-001)

This section does not re-litigate the data-path fork. It records how the verdicts above map onto the unified baseline and whether any protocol/performance finding constitutes a D-001 challenge (i.e. evidence that the baseline as a whole cannot work).

**Baseline as adopted for this audit:**

| Layer | Baseline (07 §3.5) | Effect on this report |
|---|---|---|
| Ingress / data path | FUSE mount (go-fuse/v2) is the only application-facing path; zero/short kernel TTL + direct I/O for mutable data; userspace lease-guarded cache; invalidation on lease loss/partition. Native dirs are daemon-private backing only. | All latency/throughput math in §2 *assumes* this path (FUSE round-trip ≈0.3ms in the 25ms budget). A watcher path is not costed because it cannot deliver quorum-before-ack (07 §2 Q1) — costing it would be a category error. |
| Consensus | `go.etcd.io/etcd/raft/v3` per volume (one volume group for MVP); Ready/Advance loop with WAL+hard-state `fdatasync` before any message; snapshots before applied; `ReadIndex` barrier for strict reads; campaign/apply gated on chunk presence (Inv. 4). | §1 rows 3.1–3.7, 5.2, 6.1 audit exactly this. `hashicorp/raft` alternatives (FSM/`NotifyCh`/`AddNonvoter`) are excluded per baseline — no verdict here depends on them. |
| Transport | `quic-go` QUIC + TLS 1.3 mTLS; classed streams (raft/control/client/chunk/snapshot); Raft + lease-revocation prioritized; chunk bytes on dedicated streams, never in Raft entries; 0-RTT disabled (`syncfs/1`). | §1 row 3.7 and Gap G9 audit this. "Pipelining" is read as transport pipelining only (see C9); pull-based steady-state sync is superseded and not costed. |
| Fencing | **Raft committed term/index is the fencing token** (not Camp B's per-directory epoch). No external lease manager, no writable brick. | Row 6.2 and C6 are written against term/index fencing + FUSE invalidation as the single enforcement point (07 §3.2 correction: neither library fences the filesystem alone). A per-directory-epoch design would be a different baseline and is not audited. |
| Adopted Camp B — failure states | LEADER/FOLLOWER/FENCED/CANDIDATE/CATCHING_UP/QUARANTINED/HALTED adopted as operability states over Raft + chunk-receipt state. | Perf implication: M5-01's "no unbounded queue growth or replica lag" gate must be measured *in these states*. CATCHING_UP / QUARANTINED nodes are not voters (Inv. 4–5), so a 3-voter qualification run with one node CATCHING_UP is a 2-voter quorum run (different RTT/fsync quorum math) — the benchmark must state which state vector it ran in. C5's backpressure queue must be per-state, not global. |
| Adopted Camp B — quarantine | Quarantine for uncommitted tails (corrupt WAL/snapshot/chunk + staged-but-unreferenced chunks) adopted. | Directly supports C7/G7: staged garbage after a crash-after-receipts leader is *quarantined*, not silently reused. Performance consequence: quarantine growth must be bounded and counted as staging overhead in M5-01 (disk-full behavior already requires this). |
| Adopted Camp B — POSIX-apply vectors | Mode bits incl. setuid/setgid/sticky, chown-before-chmod, ACL/xattr/symlink/hardlink/mtime, uid/gid consistency — adopted verbatim as MVP acceptance vectors. | Protocol consequence: `Command`/`Preconditions` (Gap G4) must be able to express these apply steps atomically in one command (especially rename across two parents). Perf consequence: the 500 ops/s create/write/rename gate (§2.5) must include the chown-before-chmod ordering (an extra metadata dependency inside the single Raft entry), not just file-content bytes. |
| Adopted Camp B — witness/learner vocabulary | Third-voter topology vocabulary shared (witness vs learner; full vs metadata-only chunks is Agents 1–6). | Perf consequence: chunk-prep quorum math in §2.2 assumes 2-of-3 voters hold full chunks (median `L_c`). If the third node is metadata-only, chunk-prep quorum RTT/fsync costs change (receipts vs full payload). M5-01 must pin which witness topology it qualifies. |
| Deferred tiers | One-way async + bidirectional async modes = post-MVP tiers under separate bounded-loss/conflict contracts, never aliased to the strict volume. | None of the §11 numbers in this report may be cited as applying to an async tier. Conversely, async-tier throughput (e.g. JuiceFS writeback, DRBD Protocol A) is not evidence for or against the strict-volume p99. |

**D-001 challenge assessment — NONE FOUND.** No protocol/performance finding in this report shows the unified baseline (FUSE + etcd/raft/v3 + QUIC push/pipeline + Raft term/index fencing) to be unworkable. Every gap (G1–G10) is an *under-specification within* the baseline (retention bound, deadline, dual clock, preconditions, group-commit owner, lease wait, GC epoch, RMW workload, terminology, size caps) fixable with the corrections in §4 without a data-path, library, transport, or token change. The FUSE overhead concern (07 §2 Q2: per-op round-trip, cache discipline, stall-on-failure) is already priced as the §11 qualification gates; if qualification hardware cannot meet them, the honest response per 07 §6 is to renegotiate the SLO, not to revive the watcher path. Reopening the watcher mutation path, `hashicorp/raft` MVP selection, or epoch fencing for strict scope would require a new decision explicitly revising either the north-star contract or 07 §2 Q1's proof — this audit does not meet that bar and does not propose it.
