### Notes on C2 quorum math — worked example for 3→4→3 replacement

- Add learner (simple): configs 3 → 3 voters + 1 learner. Voter quorum stays 2-of-3.
- Promote (simple AddNode): 3 → 4 voters. Quorum becomes 3-of-4; losing 1 voter still leaves 3 → progress; losing 2 stalls (worse than 3-node 1-loss tolerance *in count*, same in practice for the targeted 1-failure model). Either way a *single* AddNode never needs joint.
- Remove departed (simple RemoveNode): 4 → 3. If removal + promotion were bundled atomically (3 old → 3 new, no 4-intermediate), that requires ConfChangeV2 with `TransitionJointImplicit` and a dual-majority window (2-of-3 old AND 2-of-3 new). **Spec §12.1 step 5 implements the 3→4→3 ladder, so joint consensus is not on the critical path at all** — spec language should reflect that, reserving true joint for future >1-voter atomic swaps. Also note 2-member hazard documented by etcd ("removing a member from a two-member cluster … cannot be removed any more") is precisely why the spec's "Two-node strong operation without an independent third voter" non-goal (§2) is correct and consistent.

### Notes on C3 — three leases that must not be conflated (R-3)

1. **Raft leader lease** (etcd CheckQuorum / ReadOnlyLeaseBased): bounded by ElectionTick/HeartbeatTick and clock drift; etcd warns unbounded drift breaks safety. Hashicorp's `LeaderLeaseTimeout→step down` is the same idea at app level.
2. **Raft ReadIndex** (`ReadOnlySafe`, default): quorum heartbeat re-confirmation — this is what §8.3 "Raft ReadIndex barrier" must mean.
3. **SyncFS client read lease** (§8.2.6, §8.3): mount cache authorization, granted/revoked via state-machine entries + invalidation acks. M2-06's "ReadIndex-backed leases" conflates (2) and (3): ReadIndex supplies a fresh read point; it does **not** by itself grant a time-bounded cache lease. Grant freshness proof (ReadIndex at grant time) vs. ongoing cache authority must be separated.

## 3. Gaps & design bugs

### G-1 (Critical) §8.4.4 over-constrains Advance → heartbeat starvation
Spec: "Advance Raft only after persistence and apply obligations are complete." Library: Advance "may be done at any time after step 1" (persistence). If chunk-fetch (seconds on a big manifest) blocks Advance, Messages (including heartbeats/MsgAppResp retries) in the next Ready batch are delayed, followers time out, elections churn; a chunk-gap follower also stops broadcasting its own rejection hints. Chunk verification belongs at the *state-machine apply layer* (don't feed unVerified entries to Pebble), not at Advance.

### G-2 (Critical) Campaign-blocking deadlock: chunk gap vs. quorum
- Spec §4.4: a node with a committed entry referencing a missing chunk "MUST NOT campaign … while such a committed entry remains unapplied."
- Scenario: 3-voter cluster, node A down, node B has the chunk gap, B is the only candidate that could restore a 2-of-3 quorum — but B cannot fetch the chunk because the only copy-holder is A (down) or the leader is partitioned away. B obeys the rule → no quorum ever restored, even though B's *log* is more up-to-date than any reachable peer's and Raft would have elected it (isUpToDate is index/term-based). This is a genuine deadlock with no specified escape hatch (`RecoverCluster`-style forced snapshot exists in hashicorp; etcd has operator snapshot install — neither is wired in the spec).
- Inverse mismatch: etcd's vote grant ignores chunk payload validity. If B *does* win (e.g., wrapper bug or direct `Campaign()` call), it becomes leader with unapplied committed entries — §8.4.3 then blocks the whole apply pipeline at that index while the log grows (etcd `MaxUncommittedEntriesSize` is the library's backstop; spec never sets it).
- Also: suppressing *campaign* does not suppress *voting*. `Step` grants votes based on `isUpToDate`; SyncFS CATCHING_UP "cannot vote" (§8.4) contradicts the library's learner-voter caveat: "learners must be allowed to cast votes … consider id=1 is a learner … only 3 can win an election … it will need 1 to vote" (raft.go). A promoted-but-not-yet-applied voter in CATCHING_UP must still vote or promotion-in-flight elections livelock.

### G-3 (Major) Snapshot format/size unspecified
§8.5: "checksummed metadata checkpoint … manifest of reachable chunks." etcd sends the *whole* raft Snapshot bytes inside a single `MsgSnap` message bounded by `Config.MaxSizePerMsg`. A metadata+manifest blob for a large volume will not fit that budget. The spec sets **none** of the required etcd `Config` knobs: `MaxSizePerMsg`, `MaxInflightMsgs`, `MaxCommittedSizePerReady`, `MaxUncommittedEntriesSize`. No streaming plan for oversized snapshots; no retention/limits for the catch-up path. Also `.spec/tasks.md` M4-01 says "resumable transfer" while raft's MsgSnap is single-shot — the wrapper must chunk/ontinue over QUIC streams with its own sequencing (ReportSnapshot semantics) or send snapshot out-of-band and only use Raft's `SnapshotMetadata`/`CreateSnapshot` locally.

### G-4 (Major) GC reachability vs. retained snapshots
§8.5: chunk collectible iff "no retained metadata snapshot, committed manifest, in-flight operation, or valid client read lease can reference it." But raft compaction (`Compact`) discards entries ≤ snapshot index; subsequent GC must respect *retained snapshots older than the compact index* and Raft `InitialState`/`ConfState` in snapshots. The spec defines no artifact-retention horizon (e.g., "retain N snapshots / M indexes"), no two-phase epoch fence for mark-and-sweep across leader changes, and `MaxCommittedSizePerReady`-style paging for manifests with huge reachability sets. Risk: premature sweep deleting a chunk still reachable from a retained snapshot fetched by a lagging learner → unrecoverable gap after compaction.

### G-5 (Major) Lease-revocation-wait is an unbounded quorum-blocking wait
§8.2.6: "A live lease holder must invalidate and acknowledge; a dead session must expire before the command can proceed." + §8.3 "waits for each live lease holder to acknowledge revocation or time out." No timeout, no deadline tie to ElectionTick, no abort path, no rule for who detects "dead." If the lease holder *is* the one request path that must be revoked (e.g., writer mount paused / host suspended — the spec elsewhere demands suspension tests), the write blocks forever, and via G-1 may also stall heartbeats. Partitioned-minority mount holding a lease can stall majority writes until partition heal. Stale-hashicorp design had the same shape (TTL + grace margin) but also had a fencing token story; current spec's "expire" is circular. Every quorum write pays this cost — §11 p99 25 ms target is unproven with an unbounded blocking step.

### G-6 (Major) Write-coordinator majority is not pinned to the membership epoch
§8.2.4 chunks "to enough current voters to form a majority," then §8.2.7 proposes to Raft. Membership may change between receipt and commit (M4-02 runs concurrently by design in M4). Receipts collected from the pre-change voter set are meaningless post-change. The spec never says to pin `ConfState` index (from `ApplyConfChange` outcomes / Ready HardState) into the `PreparedChunkReceipt` set or to re-validate after commit. Payload-before-reference invariant (§3.1) can be violated by a membership race, not by a crash.

### G-7 (Major) Crash-after-commit-before-apply needs a single atomic durable batch
§10: "verify chunks, apply exactly once, and return retained operation result." etcd guarantees only that committed entries are *delivered* (possibly re-delivered after restart unless `Config.Applied` is set). The spec must require: metadata Pebble batch + operation-result record + persisted applied index committed under one fsync discipline (`MustSync` guidance). Otherwise, crash between Pebble commit and result-record write → retry duplicates; crash between result write and applied-index persist → replay duplicates despite M2-03 "replay-safe" slogan. M2-01 (crash hooks) and M2-03/M2-05 must share one crash-boundary definition; they currently don't cite each other.

### G-8 (Minor) Vocabulary/Config mismatch pack (all silent in spec, all mandatory in code)
- `PreVote: true` required for partition-rejoin stability (C4.2); spec never mentions it.
- `CheckQuorum` semantics (leader steps down when quorum inactive) overlaps spec §4.5/§10 "Leader loses quorum" row — should be explicitly enabled, with step-down vs. "cannot commit" roles assigned.
- `ReadOnlyOption: ReadOnlySafe` required for §8.3 (§C3.2).
- `MustSync` sync discipline (§8.2.8 + §11 group-commit 0–5 ms): whether group commit batches fsyncs or each Ready with entries fsyncs is an unspecified durability/perf tradeoff.
- `MaxUncommittedEntriesSize` caps divergence growth when the leader is blocked by G-2; without it, a blocked leader accumulates unbounded log tail.
- `Campaign()` control: M2-04 must define *how* candidacy is actually suppressed (e.g., gate `Tick`→`MsgHup` generation and don't forward inbound MsgVote/MsgPreVote to `Step` while chunk-gap), not just "refuse."

## 4. Concrete corrections to the spec (proposed, not applied)

### R-1 — §8.4 harden etcd Config (new sub-section) + Advance wording
> Add to §8.4: "The etcd/raft `Config` for every volume group MUST set: `PreVote: true`, `CheckQuorum: true`, `ReadOnlyOption: ReadOnlySafe`, explicit `MaxSizePerMsg`, `MaxInflightMsgs`, `MaxCommittedSizePerReady`, and `MaxUncommittedEntriesSize` (M2-01). `MemoryStorage` MUST NOT be used in production; a custom durable `Storage` (WAL + HardState + snapshots) is required."
> Replace step 4 ("Advance Raft only after persistence and apply obligations are complete") with: "Advance the Ready batch after the persistence step completes. Committed entries whose chunks are not yet locally verified MUST NOT be fed to the state machine, but MUST NOT delay Advance, heartbeats, or message send."

### R-2 — §12.1 / `docs/architecture.md` rename "joint consensus promotion" and spell the ladder
> Replace "use Raft joint consensus to promote it" with: "promote it with a single-server `ConfChangeV2` (TransitionAuto → simple protocol): `ConfChangeAddLearnerNode` → catch-up barrier (committed index known via HardState) → `ConfChangeAddNode` → wait for `ApplyConfChange`/`AutoLeave` on the leader → verify new config committed → drain departing voter → `ConfChangeRemoveNode`. True joint consensus (dual-majority window) is required only for atomic multi-voter swaps and is out of scope for single replacements."
> Add: membership completion is observed on the leader at **apply**, not at propose; the CLI's "refuse unsafe orders" (M4-02) must check `pendingConfIndex`-equivalent state (any unapplied ConfChange in the log) before proposing the next change.

### R-3 — §8.3 pin ReadIndex semantics and separate the three leases
> Replace "Fresh reads use a Raft ReadIndex barrier or a valid leader-confirmed lease" with: "Fresh reads MUST use the raft ReadIndex in `ReadOnlySafe` mode (quorum heartbeat re-confirmation; no leader-lease or clock reliance). `ReadOnlyLeaseBased` MUST NOT be used. Client cache leases ( §8.2.6/§8.3) are a separate SyncFS mechanism: grant freshness is proven by a ReadIndex barrier at grant time, but ongoing cache authority derives solely from lease generation + revocation acks, never from raft leadership state."
> Add revocation deadline: conflicting commit MUST wait at most `min(ElectionTick, lease TTL) + grace` for revocation acks; on timeout the leader MUST fail the write (not fence silently) and record the abort in the operation journal. No write may block unbounded.

### R-4 — §4.4 / §8.4 campaign gate: wrapper design + deadlock escape hatch
> Replace "MUST NOT campaign … while such a committed entry remains unapplied" and "cannot campaign or vote" with three rules:
> 1. **Suppress candidacy:** while any committed entry references an unverified chunk, the driver MUST NOT forward `MsgHup`-generating ticks to raft and MUST NOT call `Campaign()` (log-index vote granting to others remains raft's `isUpToDate` rule).
> 2. **Vote:** a node that is a voter in its currently *applied* `ConfState` still grants votes per raft rules, even when CATCHING_UP; a node whose applied config says learner does not vote. (Fixes promotion-in-flight livelock.)
> 3. **Escape hatch:** if a chunk-gap node cannot restore quorum within one election timeout *and* is the only up-to-date candidate, operators run a forced-snapshot rescue (healthy-voter snapshot install into the gap, §8.5); the wrapper MUST expose this as an admin action (M4-02), not an automatic election.
> M2-04 acceptance: deterministic test "gap node is the only up-to-date candidate" must reach the rescue path, not an election.

### R-5 — §8.5 snapshot transfer plan + GC retention horizon
> Add: raft `Snapshot{ConfState,Index,Term}` is exchanged inside Raft `MsgSnap` and MUST be small (metadata checkpoint only, bounded by `MaxSizePerMsg`). Chunk manifests transfer on SyncFS chunk streams, hash-verified, never as Raft entries. Snapshot retention MUST pin at least the last N snapshots (M4-01), and GC's mark set MUST union reachability from all retained snapshots (not just committed indexes), the raft snapshot `ConfState`, in-flight ops, and live leases. Clarify resume semantics: Raft MsgSnap is single-shot (`ReportSnapshot` unblocks the progress state); "resumable transfer" in M4-01 applies to the chunk-manifest/chunk streams, not to `MsgSnap` itself.

### R-6 — §8.2 write coordinator: pin membership epoch
> Change step 4–5: "Receipts MUST record the voter's `ConfState` index at receipt time." Change step 8: "Before acknowledging success, re-validate that the receipt set still contains a majority of the voter set that was in force at the commit index (read from `ApplyConfChange`/HardState). If membership changed mid-write, re-prepare chunks for the new majority or abort."

### R-7 — §10 crash-after-commit: atomicity clause
> Replace "apply exactly once, and return retained operation result" with: "apply the metadata batch AND the operation-result record AND the persisted Raft applied index in one durable Pebble batch, fsynced before the operation is reported committed to the client (`MustSync` semantics). `Config.Applied` MUST be set on restart from the persisted applied index so already-applied committed entries are never re-delivered."

## 5. §6 library choice — verdict on the tradeoff (aligned to D-001)

The current selection (**go.etcd.io/etcd/raft/v3**, §6) is the correct one for this design, for a structural reason beyond maturity. Per D-001 (07 §3.2/§3.4.5) this is the MVP consensus baseline; hashicorp/raft is superseded for MVP and may only be revisited post-MVP with a *written invariants-translation proof* (payload-before-reference + refuse-to-campaign as a layer above the FSM, audited under every crash interleaving).

- SyncFS needs a hard seam between *"Raft log committed"* and *"chunks verified → state machine applied"* (§8.4.3). etcd's `Ready`/`CommittedEntries`/`Advance` model is exactly that seam; hashicorp's `FSM.Apply` is called from inside the library's own goroutine with no Ready batch to interpose, and its `Transport`/`NetworkTransport` assumes the library owns the peer wire (a poor fit for SyncFS's QUIC/mTLS (§8.1) + separate chunk/snapshot streams). The stale paper trail (watcher's `remount,ro` fence + EBUSY fallback) shows the hashicorp design needed app-level workarounds for storage-level fences; the FUSE design removes that entire problem class.
- etcd's published users (etcd, CockroachDB, TiDB, swarmkit) and "stable and feature complete … most widely used" claim support the §6 "Mature deterministic Raft core" rationale; license is Apache-2.0 vs. hashicorp's MPL-2.0.
- Stale hashicorp specifics — `AddNonvoter` "witness" voters, per-directory lease epochs, `LeaderCh`-driven self-fencing, `LeaderLeaseTimeout` stepdown — have **no counterparts** in the current spec (no witness role, no per-directory lease epochs; §4.8 learners don't vote; leadership fencing is by committed term/index per §8.4). Any implementation work sourced from those docs would violate §2/§5.

One counterweight to note honestly: hashicorp provides `BootstrapCluster`/`RecoverCluster` (with explicit unsafe-recovery warnings) and `VerifyLeader` (stale-read guard) out of the box; with etcd/raft, SyncFS must build the bootstrap path, quorum-loss operator recovery, and read staleness guards itself (tasks M4-01/M4-02/M4-03 own that work).

## 5bis. Adopted-term mapping against the D-001 baseline (D-001 does not relitigate these)

The taxonomy adopted from Camp B must be a **projection** over etcd raft state + SyncFS receipt/integrity state, never an independent authority. Required projection (feeds R-4):

| Adopted state | Source of truth (primary) | Vote | Campaign |
|---------------|---------------------------|------|----------|
| LEADER | raft `StateLeader` (SoftState) + quorum active (CheckQuorum) | — | — |
| FOLLOWER | raft `StateFollower`/`StateCandidate`, applied ConfState says voter, apply caught up | per `isUpToDate` | yes (when it wins) |
| FENCED | follower/candidate with lost quorum, lease expired, or control-conn loss (spec §10 partition semantics) | per `isUpToDate` | per R-4 gate only |
| CANDIDATE | raft `StateCandidate`/`StatePreCandidate` (PreVote) | — | already campaigning |
| CATCHING_UP | applied ConfState says learner, or applied index lagging committed index, or chunk-gap gate active | **iff applied config says voter** (C8.1 caveat) | **no** (R-4 suppression) |
| QUARANTINED | integrity failure (§4.9): hash/WAL/cert/format violation detected | no (must be removed from effective voters by admin repair, not by silent self-heal) | no |
| HALTED | safety trip (marker/mass-delete/disk error) | no | no |

**Witness vocabulary rule (C8.2):** "witness" is adopted as *vocabulary only* in MVP. There is no etcd raft witness role (proto `ConfState` has voters/learners only). If a future amendment introduces a metadata-only voter, Inv.3's chunk quorum must be redefined over the data-bearing subset — that is a separate spec decision (Agents 1–6), flagged here so nobody reads "witness" as a raft election role. Pull-based catch-up likewise survives only as follower/learner replay under commit semantics (D-001), and the watcher survives only as an integrity tripwire over daemon-private backing dirs — neither changes the QUIC push/pipeline data plane.

## 7. Honesty note — what the spec claims without evidence

1. **§11 performance targets** (1,000 ops/s p99 ≤ 25 ms quorum write; 500 ops/s p99 ≤ 30 ms create/write/rename; 2 ms cache-hit reads) are asserted as qualification gates with no benchmark, no reference-harness, and no interaction analysis (e.g., the §8.2.6 revocation wait sits squarely in the write path — G-5). Status: *unproven intent*, not evidence. They must not be cited as achieved properties.
2. **§8.5 "atomically activates it, then replays subsequent entries"** asserts an atomic-replace guarantee for the receiver install with no durable two-phase activation design (write-to-temp → verify → rename → persist active generation pointer → fsync dir). Gaps of exactly this shape are where snapshot installs lose committed state (see §10 quarantine row, which promises "rebuild from a healthy snapshot" but never defines the active-generation durability rule).
3. **§4.7 "bounded result record"** never states the bound, eviction rule, or its relation to client journal retention. An unbounded-eviction table silently resurrects double-apply on retry after eviction — the exact failure §3.6 ("concurrent retries cannot double-apply") claims to prevent.
4. **§8.4 "no external lease manager … to fence"** is a true and sufficient statement for the *storage* plane, but it elides the §8.3 mount-cache lease manager, which *is* an external (leader-driven) fencing authority for readers. The spec should say: storage fencing by term/index; reader fencing by cache-lease revocation — two mechanisms, two failure stories.
5. **§12.1 "The CLI must refuse unsafe orders rather than relying on operator memory"** has no defined refusal predicate (which raft state is checked? `pendingConfIndex`? committed-index lag? snapshot readiness?). Per C2.2, "promoted" must mean *applied on the leader*, not proposed — the gap is filled by R-2 above.
6. **Witness vocabulary (post-D-001):** D-001 adopts "witness/learner" vocabulary and defers full-vs-metadata-only to Agents 1–6, but neither the current spec nor any primary source defines a voting-but-dataless raft role — etcd `ConfState` has voters/learners only (C8.2). Until an amendment splits Inv.3's chunk quorum from raft quorum, "witness" is vocabulary for the third full voter, not a topology claim.
7. **Paper-level citations:** this report's C7 verdict rests on the etcd implementation of the Raft thesis (which cites §4.3 for joint consensus and §9.6 for PreVote), not on fetched paper text; the PDF was unfetchable in this environment. Any future spec revision that quotes the paper directly must re-verify the quotes against the PDF/dissertation text.
